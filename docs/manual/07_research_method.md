# 第 7 章　研究方法：之後可以重複使用的步驟

> **本章重點**
> - 把這次「從一篇 paper 到可執行的實驗」的過程，整理成**可以套用到任何架構／加速器 paper** 的流程。
> - 每一步都附上 checklist，以及本專題的實際做法當範例。
> - 你之後的研究會從 LightNobel 延伸，這一章就是每次讀新 paper 時的操作手冊。

---

## 7.1 整體流程

```
 ① 讀 paper：抓出「問題 → 觀察 → 解法 → 評估」
        │
        ▼
 ② 量化問題：算出資料量、運算量、算術強度
        │
        ▼
 ③ 縮小範圍：挑一個能代表問題、做得完的核心
        │
        ▼
 ④ 設計實驗：對照組 + 一次只改一個變數
        │
        ▼
 ⑤ 實作與驗證：從快到慢（模擬 → 合成 → 上板）
        │
        ▼
 ⑥ 分析：找瓶頸、解釋為什麼（roofline、Amdahl）
        │
        ▼
 ⑦ 呈現：圖表與結論
```

## 7.2 步驟一：讀 paper 的方法

### 四個問題（每篇都要能回答）
| 問題 | 要找的內容 | LightNobel 的答案 |
|---|---|---|
| **問題是什麼？** | 什麼東西不夠好？具體的限制 | PPM 無法處理長序列，因為 activation 記憶體隨 L² 成長 |
| **他們觀察到什麼？** | 讓解法成立的關鍵事實（通常有分析圖） | 長序列時時間集中在 pair representation（尤其 Triangle Attention）；瓶頸是 activation 不是權重；channel 之間差異小、token 之間差異大；不同位置的 activation 特性不同 |
| **解法是什麼？** | 演算法 + 硬體 | Token-wise 自適應量化 + 專用加速器 |
| **怎麼證明有效？** | 比較對象、指標、資料集 | 與 GPU 基準比較記憶體、速度、準確度、可支援的序列長度 |

### 閱讀順序（不要從頭讀到尾）
1. **標題、摘要**：一句話說出問題與解法。
2. **Introduction 的最後一兩段**：通常會列出貢獻（contributions）。
3. **動機（Motivation）章節的圖**：這裡是「觀察」，最重要。
4. **評估（Evaluation）的主要圖表**：看比較對象和提升幅度。
5. **方法章節**：前面都懂了，再看細節。
6. **Related work**：找出這個領域還有哪些相關論文，建立文獻地圖。

### 讀完要寫下的筆記模板
（「速覽」一章就是用這個模板整理 LightNobel 的完整範例。）

```
論文：
一句話摘要：
問題（附具體數字）：
關鍵觀察（附圖號）：
解法：
  - 演算法層面：
  - 硬體層面：
評估：
  - 比較對象：
  - 主要指標與結果：
  - 資料集／模型：
我可以重現／延伸的部分：
我不確定的地方（要回原文確認）：
```

## 7.3 步驟二：量化問題

**任何「效能」問題，都先算這三個數字：**

| 數字 | 怎麼算 | 本專題的例子 |
|---|---|---|
| **資料量** | 每個張量的形狀 × 每個元素的 bytes | pair tensor = L² × 128 × 4 bytes（L = 1000 時 512 MB） |
| **運算量** | 數迴圈：每個輸出要幾次乘加 | 2 × L³ × C FLOP（L = 1000 時約 2.6 × 10¹¹） |
| **算術強度** | 運算量 ÷ 實際搬運量 | 直白寫法 0.25，tiling 後 2～8 FLOP/byte |

然後和硬體比：
```
硬體平衡點 = 峰值運算能力 ÷ 記憶體頻寬

算術強度 < 平衡點 → memory-bound → 優先減少搬運
算術強度 > 平衡點 → compute-bound → 優先增加運算單元
```

### Checklist
- [ ] 找出最大的張量是哪一個，它隨什麼參數成長（L？L²？L³？）
- [ ] 找出運算量最大的運算
- [ ] 計算不同規模（L = 256、1000、4000）下的數字，做成表格
- [ ] 判斷是記憶體容量、記憶體頻寬還是運算能力的問題

## 7.4 步驟三：縮小範圍

### 好的範圍要滿足
| 條件 | 為什麼 | 本專題 |
|---|---|---|
| **能代表 paper 的問題** | 結論才有意義 | Triangle Multiplication 直接處理 L² 的 pair tensor |
| **算式清楚、容易驗證** | 能確認做對了 | 本質是矩陣乘法，可以用 CPU 算正確答案 |
| **能和原始模型對上** | 證明不是自己亂編的 | 用 ESMFold 驗證算式差值 0 |
| **大小做得完** | 時間有限 | 只做 einsum，不做 LayerNorm/gating |
| **能展示多種手法** | 才有比較 | 五種記憶體手法都適用 |

### 常見的縮小方式
- **只做一個運算**（本專題的做法）
- **只做一種資料精度**
- **固定部分參數**（例如固定 C = 128，只讓 L 變動）
- **用模擬資料代替真實資料**，但要說明模擬資料的特性為什麼合理（例如我們加了 1% outlier）

## 7.5 步驟四：設計實驗

### 原則一：一定要有對照組（baseline）
沒有 baseline，「快了 3 倍」就沒有意義。本專題的 **v0** 就是 baseline：最直白、沒有任何優化。

### 原則二：一次只改一個變數
```
v0 ──(+ tiling)──► v1 ──(+ 寬位元)──► v2 ──(+ double buffering)──► v3
                                        └──(+ 量化)──► v4
```
每一版只多一招，才能說「這個改善來自這一招」。
**v4 是從 v2 分出來的，不是從 v3。** 這樣 v4 和 v2 的差異就只有量化。

### 原則三：掃描參數，不要只看一個點
| 掃描 | 看什麼 |
|---|---|
| Tile 大小（4、8、16、32） | 搬運量 vs 晶片內記憶體的 trade-off |
| 序列長度 L（128～2048） | 時間是否符合 L³、記憶體是否符合 L² |
| HBM 設定（多通道 vs 單一） | 頻寬的影響 |

### 原則四：同時量「好處」和「代價」
| 好處 | 代價 |
|---|---|
| 時間、GFLOP/s、頻寬 | 硬體資源（BRAM、DSP、LUT、FF） |
| 可支援的最大 L | 精度損失（rel_l2） |
| 記憶體佔用 | 程式複雜度 |

### Checklist
- [ ] 定義 baseline
- [ ] 每個版本只改一件事，並寫下「預期會改善什麼、為什麼」
- [ ] **先預測再量測**（例如：v3 預測快約 21%）
- [ ] 列出要掃描的參數
- [ ] 列出要記錄的指標（好處＋代價）

## 7.6 步驟五：實作與驗證

### 從快到慢
| 階段 | 時間 | 驗證什麼 | 失敗了怎麼辦 |
|---|---|---|---|
| C 模擬 | 秒 | 算得對不對 | 修演算法 |
| HLS 合成 | 分鐘 | 能不能變成電路、速度和資源估計 | 修 pragma、改寫法 |
| C/RTL 協同模擬 | 分鐘～小時 | 電路和 C++ 一致嗎 | 檢查 DEPENDENCE 等宣告 |
| 硬體模擬 | 小時 | 整個系統的介面 | 修 host 或設定 |
| 上板 | 1～數小時編譯 | 真實速度 | 修時序、記憶體設定 |

**前一步沒過，不進下一步。**

### 驗證正確性的技巧
1. **用高精度（double）算參考答案**。
2. **用相對誤差**（rel_l2）而不是絕對誤差，因為數值大小不一。
3. **測試多種大小與設定**：我們測了 L = 16、32、48、64，以及 8×8、16×4、32×32 的 tile。
4. **刻意加入困難的情況**：outlier 就是為了讓量化的差異顯現出來。
5. **和原始模型對照**：ESMFold 的「差值 0」驗證。

## 7.7 步驟六：分析

### 找瓶頸的方法
1. 看報告中**每個迴圈的 cycle 數**，找出佔最多時間的部分。
2. 算出**各部分的比例**（例：v2 中載入佔 141 / 671 ≈ 21%）。
3. 用 **Amdahl's Law** 算出改善那一部分的上限。
4. 在 **roofline 圖**上標出位置，判斷是 memory-bound 還是 compute-bound。

### 解釋結果時要回答
- 結果和預測一致嗎？不一致的話，為什麼？
- 瓶頸轉移到哪裡了？
- 付出的代價（資源、精度）值得嗎？
- 在真實情況下（更大的 L、真實資料）結論還成立嗎？

## 7.8 步驟七：呈現（報告要畫的圖）

| 圖 | x 軸 | y 軸 | 要傳達的訊息 |
|---|---|---|---|
| **動機圖** | L | 記憶體（GB） | 記憶體隨 L² 爆炸（問題的嚴重性） |
| **各版本比較** | v0～v4 | 時間（對數軸）或加速倍數 | 每一招的效果 |
| **Roofline** | 算術強度（對數） | GFLOP/s（對數） | 每一招讓 kernel 往哪裡移動 |
| **時間拆解** | 版本 | cycle（堆疊長條：載入／計算／其他） | 瓶頸在哪、怎麼轉移 |
| **Tile sweep** | tile 大小 | 時間 ＋ BRAM 用量（雙 y 軸） | trade-off |
| **量化精度** | 量化方式 | rel_l2 | per-token vs per-tensor |
| **資源用量** | 版本 | BRAM／DSP／LUT 百分比 | 代價 |

## 7.9 除錯的思路（以 2025.2 路徑 bug 為例）

```
1. 讀完整的錯誤訊息（包括 WARNING）
      ↓ 「Cannot find source file ../kernels/trimul_v2.cpp」
2. 比較預期和實際
      ↓ 預期是 kernels/trimul_v2.cpp，實際變成 ../kernels/...
3. 提出假設並修正
      ↓ 假設：相對路徑的問題 → 改成絕對路徑
4. 修正無效 → 假設錯了，找新線索
      ↓ 日誌顯示加入時是絕對路徑，但合成時又被改寫
5. 用算的驗證新假設
      ↓ 專案在下兩層，但工具只往上一層 → 工具假設專案只在下一層
6. 針對根因修正
      ↓ 從 hls_prj 裡面建立專案 → 成功
```

### 回報問題時的好習慣（對學長姐、助教或 Claude 都適用）
- 附上**完整的指令**和**錯誤前後的 20～30 行輸出**。
- 說明**預期會發生什麼**。
- 說明**已經試過什麼**。
- 附上環境資訊（工具版本、作業系統）。

## 7.11 案例：讀原文後發現的三個誤判

本專題一開始無法下載 LightNobel 原文，對論文的理解來自摘要和搜尋結果。拿到 PDF 讀完後，發現三個誤判：

| 誤判 | 原本以為 | 原文（出處） | 影響 |
|---|---|---|---|
| ① 哪個運算最花時間 | Triangle Multiplication 是最核心、最吃資源的運算 | 長序列時 Triangle Attention 佔 75.9%，Triangle Multiplication 只佔 14.5%（Fig. 3） | 選題理由改成「結構最單純的第一個目標」，Triangle Attention 列為未來工作 |
| ② 我們的新意在哪 | 融合是和 LightNobel「互補」的新角度 | RMPU → VVPU 的管線與執行時量化已經做到中間值不落地（Sec. 5） | 貢獻改成「FPGA 實作 ＋ 拆解每一招 ＋ 分析模型」 |
| ③ 比較基準 | 以 FP32 計算量化的效果 | 基準是 FP16（Table 1） | 容量提升從 1.67 倍改成 1.52 倍 |

另外還有一個**新發現**：a、b 屬於論文的 C 組（INT4、不處理 outlier），所以 INT4 的 v5 變成有依據的下一步。

### 學到的事
1. **二手資料只能當線索**：摘要、新聞稿、別人的整理都會省略細節。做決策前一定要讀原文，至少讀動機的圖、方法的表格和評估設定。
2. **特別檢查三種東西**：

    - 瓶頸的數據（哪個運算、在什麼條件下量的：GPU 型號、序列長度、有沒有分塊）；
    - 比較基準（baseline 用什麼精度、什麼設定）；
    - 論文**已經做了什麼**（避免把別人做過的事當成自己的新意）。

3. **誤判不可怕，要留下紀錄**：把「原本以為 → 原文 → 修正」寫下來（`docs/PROJECT_LOG.md` 8.1 節），之後接手的人才知道為什麼策略是現在這樣。
4. **修正後要通讀一次**：一個前提改了，會影響很多章節的說法。只改有問題的句子，其他段落的邏輯可能就接不上。

## 本章小結

- **讀 paper**：問題 → 觀察 → 解法 → 評估，先看動機的圖。
- **量化**：資料量、運算量、算術強度，和硬體平衡點比較。
- **實驗**：有 baseline、一次改一件事、先預測再量測、同時記錄好處和代價。
- **驗證**：從快到慢，前一步沒過不進下一步。
- **分析**：找出比例、用 Amdahl 算上限、在 roofline 上看位置。
- **核對原文**：二手資料只當線索；特別檢查瓶頸數據、比較基準、論文已經做了什麼（7.11）。
