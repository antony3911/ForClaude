# 第 3 章　資料流優化：少搬、搬得快、不存中間值

> **本章重點**
> - 資料流優化**不改變資料格式**，只改變資料「怎麼搬、放在哪、什麼順序算、存不存」。
> - **Tiling** 減少搬運總量；**寬位元與 burst** 提高每次搬運的效率；**double buffering** 把等待藏起來；**多通道 HBM** 多條路同時搬。
> - **融合**讓中間值不寫回記憶體；**重算**用計算換記憶體；**分塊**與 **token-wise attention** 也是同一類想法。
> - 每一招都對應第 2 章時間公式裡的一項，也都有代價。

---

## 3.1 Tiling／資料重用：減少搬運總量（v0 → v1）

### 白話直覺
v0 每用一次食材就跑一趟倉庫。
v1 **一次搬一批到料理台，把這批能做的菜都做完**，再搬下一批。

### 為什麼能重用？
看算式 `z[i][j][c] = Σ_k a[i][k][c] × b[j][k][c]`：
- `a[i][k][c]` 會被**所有的 j** 用到（L 次）。
- `b[j][k][c]` 會被**所有的 i** 用到（L 次）。

如果一次處理 **TI 個 i** 和 **TJ 個 j**（一個 tile），那搬進來的每個 `a` 可以用 TJ 次，每個 `b` 可以用 TI 次。

```
          j0 ... j0+TJ−1
        ┌────────────────┐
  i0    │                │
  ...   │  一個 tile：   │   ← 輸出 z 的 TI × TJ 格，累加值放在晶片內
  i0+TI │  TI × TJ 格    │
        └────────────────┘

  對每個 k：
    搬 a[i0..i0+TI−1][k][:]   （TI × C 個數）
    搬 b[j0..j0+TJ−1][k][:]   （TJ × C 個數）
    做 TI × TJ × C 次乘加     ← 每個 a 用 TJ 次、每個 b 用 TI 次
```

### 公式推導：總搬運量
**v0（沒有重用）：** 每次乘加讀一個 a 和一個 b。
```
讀取次數 = 2 × L³ × C    （每個 z[i][j][c] 要 L 次乘加）
```

**v1（tiling）：**
```
tile 的數量            = (L/TI) × (L/TJ)
每個 tile、每個 k 的讀取 = (TI + TJ) × C
k 的數量               = L

讀取次數 = (L/TI) × (L/TJ) × L × (TI + TJ) × C
        = L³ × C × (1/TI + 1/TJ)
```

**比值：**
```
v0 / v1 = 2 ÷ (1/TI + 1/TJ)

TI = TJ = 8  → 2 ÷ (1/8 + 1/8)  = 8 倍
TI = TJ = 16 → 2 ÷ (1/16 + 1/16) = 16 倍
TI = TJ = 32 → 32 倍
```

**算術強度：**
```
AI = 2·L³·C ÷ (4 bytes × L³·C·(1/TI + 1/TJ))
   = TI·TJ ÷ (2·(TI + TJ))

8×8   → 64 ÷ 32   = 2  FLOP/byte
16×16 → 256 ÷ 64  = 4  FLOP/byte
32×32 → 1024 ÷ 128 = 8 FLOP/byte
```

### 代價：晶片內記憶體
累加器要放下整個 tile 的輸出：`TI × TJ × C` 個 float。
| Tile | 累加器大小 | 佔晶片內記憶體 |
|---|---|---|
| 8×8 | 8,192 個 float = 32 KB | 很少 |
| 16×16 | 32,768 個 = 128 KB | 少 |
| 32×32 | 131,072 個 = 512 KB | 開始明顯 |

**Tile 越大 → 搬運越少，但晶片內記憶體用越多。** 這就是 tile size sweep 實驗要量的 trade-off。

### 這是「解法」的原因
Tiling 不改變計算結果，只改變**計算順序**，卻讓**搬運總量**直接除以 4～16 倍。
這是所有矩陣運算加速器（GPU 的 cuBLAS、TPU、LightNobel 的運算單元）都會用的基本手法。

## 3.2 寬位元與 burst：提高每次搬運的效率（v1 → v2）

### 白話直覺
v1 雖然減少了趟數，但推車很小，一次只能載 **1 個 float（32 bit）**。
v2 換成大推車，一次載 **16 個 float（512 bit）**，並且 16 個廚師同時切。

### 兩個不同的概念：頻寬 vs 延遲
| 概念 | 意義 | 比喻 |
|---|---|---|
| **頻寬（bandwidth）** | 每秒能搬多少 byte | 高速公路有幾線道 |
| **延遲（latency）** | 從發出請求到拿到第一筆資料要多久 | 從家裡開到倉庫要多久 |

一條 AXI 連接埠（FPGA kernel 連到 HBM 的介面）：
```
頻寬上限 = 位元寬度 × 時脈
  32-bit  × 300 MHz = 1.2 GB/s   （v1）
  512-bit × 300 MHz = 19.2 GB/s  （v2）← 16 倍
```

### Burst（連續搬運）
每次向 HBM 發出請求都要付一次延遲。如果**要的資料在記憶體中是連續的**，可以一次請求、連續拿很多筆，這叫 **burst**。

```
非 burst：請求 → 等 → 拿 1 筆 → 請求 → 等 → 拿 1 筆 → ...   （每筆都付一次延遲）
Burst：   請求 → 等 → 拿 1 筆、1 筆、1 筆、1 筆 ...          （只付一次延遲）
```

**這就是為什麼資料排列（memory layout）很重要：** 我們把資料排成 `[row][col][channel]`，
同一個 token 的 128 個 channel 是**連續的**，所以一次可以 burst 讀完。
v0 在最內層迴圈改變 k，每次跳過 128 個數字（stride = C），**無法形成有效的 burst**，這也是它慢的原因之一。

### Little's Law：要多少資料「在路上」才能用滿頻寬
```
在途資料量 = 頻寬 × 延遲
```
例：頻寬 19.2 GB/s、延遲約 64 cycles（300 MHz 下約 213 ns）
→ 需要約 4 KB 的資料同時在路上，才能讓頻寬不空轉。
**一次只要一小筆、等到了才要下一筆，永遠用不滿頻寬。** 這也說明了 burst 和下一節 double buffering 的重要性。

### 這是「解法」的原因
寬位元讓**每個 cycle 能搬的量**變 16 倍；burst 讓**延遲只付一次**。
兩者結合，同樣的搬運量所需的時間大幅下降。同時，因為一次拿到 16 個數，也能讓 16 個運算單元同時工作，
**運算能力也跟著提高 16 倍**（v2 理論上限 = 16 × 2 × 300 MHz = 9.6 GFLOP/s）。

## 3.3 Double buffering：把等待時間藏起來（v2 → v3）

### 白話直覺
v2 的廚師：**搬一批 → 煮一批 → 搬下一批 → 煮下一批**，搬的時候廚師在等。
v3 多準備一個料理台：**廚師煮第 k 批的同時，助手把第 k+1 批搬到另一個料理台**。

```
v2（沒有重疊）：
  時間 ──────────────────────────────────────────────►
  [搬 k=0][ 算 k=0 ][搬 k=1][ 算 k=1 ][搬 k=2][ 算 k=2 ]

v3（double buffering，兩組 buffer 輪流用）：
  [搬 k=0][ 算 k=0 ][ 算 k=1 ][ 算 k=2 ][ 算 k=3 ]
          [搬 k=1]  [搬 k=2]  [搬 k=3]
           ↑ 搬運藏在計算底下
```

### 用實際數字看：v2 的 HLS 報告
每一輪 `loop_k`：
| 步驟 | cycles |
|---|---|
| 載入 a、b（兩個並行） | 141 |
| 計算（mac） | 526 |
| **合計** | **約 671** |

套用 2.4 節的公式：
```
v2（輪流）：T ≈ T_compute + T_memory = 526 + 141 ≈ 671 cycles
v3（重疊）：T ≈ max(T_compute, T_memory) = max(526, 141) ≈ 530 cycles

時間減少 ≈ (671 − 530) ÷ 671 ≈ 21%     → 速度約 1.27 倍
```

### 為什麼上限只有約 21%？
因為**搬運只佔 21% 的時間**。即使把搬運完全藏起來，最多也只能省下這 21%。
這是 **Amdahl's Law** 的例子（見 2.6 節）。

### 延伸觀察：141 cycles 裡大部分是「延遲」
v2 每輪只搬 2 × 64 = 128 個 512-bit word（a、b 各 64 個，兩個 port 並行），
理想上只要約 64 cycles，但報告顯示 141 cycles。
多出的時間大多是 **HBM 的延遲**（HLS 預設假設 64 cycles）和迴圈的啟動成本。
**Double buffering 對付的正是這種「延遲型」的等待**：延遲再長，只要能和計算重疊，就不會影響總時間。

### 這是「解法」的原因
Double buffering 不減少搬運量，也不提高頻寬，而是**改變時間的結構**：
從「相加」變成「取最大值」。當計算和搬運的時間接近時，效果最好（最多快 2 倍）。

## 3.4 多通道 HBM：多條路同時搬

### U55C 的 HBM 結構
```
16 GB HBM2 = 32 個 pseudo-channel（PC），每個 512 MB、約 14 GB/s
            ┌────┬────┬────┬─────┬────┐
            │PC0 │PC1 │PC2 │ ... │PC31│
            └────┴────┴────┴─────┴────┘
             總頻寬約 460 GB/s（全部同時用的情況下）
```
**單一 PC 的頻寬和容量都不大**，要同時使用多個 PC，才能發揮 HBM 的優勢。

### 本專題的兩種設定
| 設定檔 | a | b | z | 預期效果 |
|---|---|---|---|---|
| `trimul_v2.cfg` | PC 0～7 | PC 8～15 | PC 16～23 | 三份資料走不同的路，互不干擾 |
| `trimul_v2_onebank.cfg` | PC 0 | PC 0 | PC 0 | 三份資料搶同一條路 |

### 這是「解法」的原因
頻寬是「每條路的頻寬 × 同時使用的路數」。讓不同資料走不同的 PC，
等於把公式中的 `頻寬` 乘上倍數；反之，全部擠在同一個 PC 會互相排隊。
這個實驗需要**上板**才看得出效果（HLS 報告無法模擬 HBM 的真實行為）。

## 3.5 運算融合：讓中間值不寫回記憶體

前面幾節的例子（v0～v3）只處理中間的 einsum。實際上 ESMFold 的 Triangle Multiplication（outgoing）是這樣：

```
  z（輸入，L×L×128）
  │
  ├─ LayerNorm ─────────────────► z_ln
  │                                 │
  │        ┌────────────┬───────────┼───────────┬────────────┐
  │        ▼            ▼           ▼           ▼            ▼
  │    linear_a_p   linear_a_g  linear_b_p  linear_b_g    linear_g
  │        │            │ sigmoid   │           │ sigmoid    │ sigmoid
  │        └──── × ─────┘           └──── × ────┘            │
  │              │ × mask                 │ × mask           │
  │              ▼                        ▼                  │
  │              a                        b                  │
  │              └───────── einsum ───────┘                  │
  │                  z_ij = Σ_k a_ik · b_jk                  │
  │                           │                              │
  │                     LayerNorm_out                        │
  │                           │                              │
  │                       linear_z                           │
  │                           └────────────── × ─────────────┘
  │                                           │
  └──────────────────────── + ◄───────────────┘   （residual，在 block 外面加）
                                              ▼
                                            輸出
```

每一個箭頭的結果都是 **L × L × 128** 的張量。
這些 linear 都是「**每個 token 各自**做 128×128 的矩陣乘法」，不同 token 之間互不相干。

### 一般實作會「落地」多少資料？
如果每個運算都是獨立的函式（PyTorch 預設的做法），每一步的結果都要**寫回記憶體**，下一步再讀出來。
同一時間存在的 pair 張量，峰值大約是 **7 份**（z、z_ln、a、b、g、einsum 的結果、各種暫存）。
GPU 上的融合實作分析也是這個量級（見 10.6 節的參考資料）。

### 白話直覺
**不融合：** 廚師切完洋蔥放回倉庫，另一個廚師再從倉庫拿出來炒。
**融合：** 切完直接下鍋，洋蔥**不回倉庫**。

### 正式說法：producer–consumer
- **Producer**：產生資料的運算（例如 linear_a_p）。
- **Consumer**：使用資料的運算（例如 gating 的乘法）。
- 如果 consumer 在 producer 產生資料後**馬上**用掉，資料就可以留在晶片內（暫存器、BRAM），不必寫回 HBM。
- 這個「產生到使用之間的距離」叫做 **reuse distance**。距離越短，越容易融合。

### 為什麼 Triangle Multiplication 適合融合
LayerNorm、5 個 linear、sigmoid、gating、量化，**全部都是「每個 token 自己算自己的」**：
```
token (i, k) 的 128 個數
   → LayerNorm（只需要這 128 個數的平均與變異數）
   → 5 個 128×128 linear（只需要這個 token ＋ 權重）
   → gating、mask、量化（只需要這個 token）
```
一個 token 的所有處理都可以在晶片內完成，**只有最後的 a、b 需要寫出去**（因為 einsum 需要跨 token 的資料）。

> **和 LightNobel 的關係：** LightNobel 的硬體就是以 token 為單位流動：RMPU 算完 linear，結果以管線方式直接交給 VVPU
> 做 LayerNorm、gating、量化，中間值不寫回外部記憶體（Sec. 5）。本節是**同一個原則**在 Triangle Multiplication 上的具體展開，
> 並額外算出流量與容量各省多少——論文只給整體結果，沒有拆開。

本專題把這個原則落實成兩個 kernel 的設計，並估算流量與容量各省多少，見第 10 章 10.3 節。

## 3.6 重算：用計算換記憶體

### 問題
g = sigmoid(linear_g(LayerNorm(z))) 在最後才會用到。如果在 producer 算好存起來，就要多存一份 L×L×128。

### 做法：在 consumer 的 epilogue 從 z 重新算
**多花的計算：** 每個輸出位置要多做一次 128×128 的 linear。
```
重算 g 的運算量    = 2 × C² = 2 × 128 × 128 ≈ 32,768 FLOP / 每個輸出位置
einsum 本身的運算量 = 2 × L × C = 256 × L FLOP / 每個輸出位置

比例 = 32,768 ÷ (256 × L) = 128 ÷ L
  L = 256  → 50%
  L = 1024 → 12.5%
  L = 4096 → 約 3%
```
**序列越長，重算的代價越小**，而省下的記憶體（每個 L² 512 bytes）越重要。這正好就是長序列的情境。

### 一般原則：Recomputation
「**不存、需要時再算**」是記憶體不夠時的常見手法（訓練大型模型時的 activation checkpointing 也是同樣的想法）。
判斷值不值得的方法：
```
值得重算 ⇔ 重算的時間 < 存取它所需的時間，或 記憶體容量是瓶頸
```

## 3.7 分塊、token-wise attention 與其他手法

**分塊（chunking）可以看成「更上一層的 tiling」**：tiling 把資料切小，放進晶片內的記憶體；chunking 把計算切小，讓中間值放得進 GPU／HBM。兩者的取捨相同：切得越小，峰值記憶體越低，但另一邊的資料要重複讀越多次。

除了前面幾節，還有幾種常見手法（v0～v4 沒有用到，但讀論文、做報告時會遇到）：

| 手法 | 原理 | 代價 | 在 PPM 的例子 |
|---|---|---|---|
| **Chunking（分塊）** | 一次只算一部分，算完就丟 | 時間變長 | AlphaFold2/ESMFold 內建 chunk size 設定；LightNobel 的 GPU 比較對象用 Chunk4 |
| **Token-wise attention** | attention 一次處理一部分 token，不存整個 score matrix | 要線上追蹤最大值 | LightNobel 的 Triangle Attention（原理見 6.6 節的線上 softmax） |
| **低精度浮點（FP16/BF16）** | 每個數用 2 bytes | 範圍或精度下降 | ESMFold 的基準精度就是 FP16；更低的位元數見第 4 章 |
| **稀疏化** | 跳過接近 0 的值 | 需要不規則存取 | 距離很遠的 (i, j) 對 |

## 3.8 總整理：每一招解決了什麼

| 問題 | 手法 | 從什麼概念上解決 |
|---|---|---|
| 搬運太多 | Tiling | 利用資料重用，減少重複搬運 |
| 搬運沒效率 | 寬位元、burst | 每次搬更多、延遲只付一次 |
| 等待延遲 | Double buffering | 讓搬運和計算重疊 |
| 頻寬不夠 | 多通道 | 同時使用多條路 |
| 資料太大、放不下 | 量化（第 4 章） | 每筆資料變小，同時降低容量與頻寬需求 |
| 中間值太多 | 融合、重算（3.5、3.6 節） | 中間值不寫回記憶體 |

## 本章小結

| 手法 | 縮小時間公式的哪一項 | 代價 | 本專題 |
|---|---|---|---|
| Tiling | 搬運量 ↓ | 晶片內記憶體 | v1 |
| 寬位元、burst | 頻寬 ↑、等待次數 ↓ | 介面與運算單元變多 | v2 |
| Double buffering | `+` 變成 `max` | 兩組 buffer | v3 |
| 多通道 HBM | 頻寬 ↑ | 要上板才看得到 | cfg 對照 |
| 融合、重算 | 中間值的份數 ↓ | 設計複雜、多花計算 | 第 10 章的設計 |

效益不大時，通常是**瓶頸轉移**了（2.6 節），這本身就是有價值的發現。
