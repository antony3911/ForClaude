# 第 2 章　為何可做：這些解法從什麼概念上解決問題？

> **本章重點**
> - 所有記憶體優化都可以用一條「時間公式」來理解：**每一招都在縮小公式裡的某一項**。
> - **算術強度**與 **Roofline 模型**用來判斷瓶頸在哪，也用來評估優化有沒有效。
> - 五個手法各自對應的概念：
>   Tiling → 減少**搬運總量**；寬位元／burst → 提高**每次搬運的效率**；
>   Double buffering → 把**等待時間藏起來**；多通道 → **多條路同時搬**；量化 → **每筆資料變小**。
> - 「效益不大」通常是因為**瓶頸轉移**了（Amdahl's Law），這本身就是有價值的發現。

---

## 2.1 一條公式看懂所有優化

一個 kernel 的執行時間，可以粗略拆成「計算」和「搬資料」兩部分：

```
如果計算和搬運「輪流」做（沒有重疊）：
    T  ≈  T_compute + T_memory

如果計算和搬運「同時」做（完全重疊）：
    T  ≈  max(T_compute, T_memory)

其中：
    T_compute = 運算次數 ÷ (每個 cycle 的運算數 × 時脈)
    T_memory  = 搬運量 ÷ 頻寬  +  每次請求的延遲 × 等待次數
```

**每一招優化，都是在縮小其中一項：**

| 手法 | 縮小哪一項 | 對應版本 |
|---|---|---|
| Tiling／資料重用 | `搬運量` ↓ | v1 |
| 寬位元、burst | `頻寬` ↑、`等待次數` ↓ | v2 |
| 平行運算單元 | `每 cycle 運算數` ↑ | v2（16 路）、v4（64 路） |
| Double buffering | 把 `+` 變成 `max` | v3 |
| 多通道 HBM | `頻寬` ↑ | cfg 對照實驗 |
| 量化 | `搬運量` ↓（每筆資料變小） | v4 |

接下來每一節都會回到這條公式。

## 2.2 記憶體階層：為什麼「搬運」有成本

### 白話直覺
離運算單元越近的記憶體，**越快但越小**；越遠的記憶體，**越大但越慢**。

```
   速度快、容量小                                         速度慢、容量大
 ┌──────────┐   ┌──────────────┐   ┌────────────────┐   ┌─────────────┐
 │ Register │ → │ 晶片內記憶體 │ → │ HBM / DRAM     │ → │ 硬碟 / 網路 │
 │ (FF)     │   │ BRAM / URAM  │   │ (板上主記憶體) │   │             │
 └──────────┘   └──────────────┘   └────────────────┘   └─────────────┘
   1 cycle        1～2 cycles        數十～數百 cycles    非常久
   約 330 KB      U55C 約 43 MB      U55C 16 GB           
```

### U55C 的具體數字
| 層級 | 容量 | 存取延遲 | 備註 |
|---|---|---|---|
| FF（暫存器） | 約 260 萬個 bit（約 330 KB） | 1 cycle | 直接接在運算單元上 |
| BRAM | 4,032 塊 × 18 Kb ≈ 9 MB | 1～2 cycles | 可同時存取很多塊 |
| URAM | 960 塊 × 288 Kb ≈ 35 MB | 1～2 cycles | 比 BRAM 大塊 |
| HBM2 | 16 GB（32 個 pseudo-channel × 512 MB） | 數十～上百 cycles | 總頻寬約 460 GB/s |

**關鍵：** 一份 L = 1000 的 pair tensor 就有 512 MB，晶片內只有約 43 MB，**不可能整份放進來**，一定得分批從 HBM 搬。

## 2.3 主軸概念：算術強度與 Roofline 模型

### 算術強度（Arithmetic Intensity, AI）
```
AI = 運算次數 ÷ 從主記憶體搬運的 byte 數      （單位：FLOP/byte）
```
意義：**每搬 1 byte，能做幾次運算**。

### Roofline 模型
硬體有兩個上限：
1. **運算上限**（每秒最多做幾次運算）：一條水平線。
2. **頻寬上限**（每秒最多搬多少 byte）：AI 越高，同樣頻寬能支撐的運算越多，是一條斜線。

```
效能
(GFLOP/s)
   │                  ┌──────────────────  ← 運算上限（屋頂）
   │                 /
   │                /   ← 頻寬上限（斜率 = 頻寬）
   │               /
   │              /
   │     ● v0    /       ● v2
   │            /
   │           /
   └──────────┴────────────────────────── 算術強度（FLOP/byte，對數軸）
         memory-bound │ compute-bound
                      ↑
                  平衡點（ridge point）
```

- 在平衡點**左邊**：被頻寬限制（memory-bound）→ 要提高 AI 或頻寬。
- 在平衡點**右邊**：被運算能力限制（compute-bound）→ 要增加運算單元。

### 可達效能的公式
```
可達效能 = min( 運算上限 ,  AI × 頻寬 )
```

### 本專題的例子
| 版本 | AI（FLOP/byte） | 說明 |
|---|---|---|
| v0 | 0.25 | 每 2 次運算讀 8 bytes |
| v1、v2、v3（8×8 tile） | 2 | 見 2.4 節推導 |
| v4（INT8，8×8 tile） | 約 7.8 | 見 2.8 節推導 |

**畫 roofline 圖是報告中最重要的圖之一**：可以一眼看出每一招讓 kernel 往哪個方向移動。

## 2.4 解法一：Tiling／資料重用 → 減少搬運總量（v0 → v1）

### 白話直覺
v0 每用一次食材就跑一趟倉庫。
v1 **一次搬一批到料理台，把這批能做的菜都做完**，再搬下一批。

### 為什麼能重用？
看算式 `z[i][j][c] = Σ_k a[i][k][c] × b[j][k][c]`：
- `a[i][k][c]` 會被**所有的 j** 用到（L 次）。
- `b[j][k][c]` 會被**所有的 i** 用到（L 次）。

如果一次處理 **TI 個 i** 和 **TJ 個 j**（一個 tile），那搬進來的每個 `a` 可以用 TJ 次，每個 `b` 可以用 TI 次。

```
          j0 ... j0+TJ−1
        ┌────────────────┐
  i0    │                │
  ...   │  一個 tile：   │   ← 輸出 z 的 TI × TJ 格，累加值放在晶片內
  i0+TI │  TI × TJ 格    │
        └────────────────┘

  對每個 k：
    搬 a[i0..i0+TI−1][k][:]   （TI × C 個數）
    搬 b[j0..j0+TJ−1][k][:]   （TJ × C 個數）
    做 TI × TJ × C 次乘加     ← 每個 a 用 TJ 次、每個 b 用 TI 次
```

### 公式推導：總搬運量
**v0（沒有重用）：** 每次乘加讀一個 a 和一個 b。
```
讀取次數 = 2 × L³ × C    （每個 z[i][j][c] 要 L 次乘加）
```

**v1（tiling）：**
```
tile 的數量            = (L/TI) × (L/TJ)
每個 tile、每個 k 的讀取 = (TI + TJ) × C
k 的數量               = L

讀取次數 = (L/TI) × (L/TJ) × L × (TI + TJ) × C
        = L³ × C × (1/TI + 1/TJ)
```

**比值：**
```
v0 / v1 = 2 ÷ (1/TI + 1/TJ)

TI = TJ = 8  → 2 ÷ (1/8 + 1/8)  = 8 倍
TI = TJ = 16 → 2 ÷ (1/16 + 1/16) = 16 倍
TI = TJ = 32 → 32 倍
```

**算術強度：**
```
AI = 2·L³·C ÷ (4 bytes × L³·C·(1/TI + 1/TJ))
   = TI·TJ ÷ (2·(TI + TJ))

8×8   → 64 ÷ 32   = 2  FLOP/byte
16×16 → 256 ÷ 64  = 4  FLOP/byte
32×32 → 1024 ÷ 128 = 8 FLOP/byte
```

### 代價：晶片內記憶體
累加器要放下整個 tile 的輸出：`TI × TJ × C` 個 float。
| Tile | 累加器大小 | 佔晶片內記憶體 |
|---|---|---|
| 8×8 | 8,192 個 float = 32 KB | 很少 |
| 16×16 | 32,768 個 = 128 KB | 少 |
| 32×32 | 131,072 個 = 512 KB | 開始明顯 |

**Tile 越大 → 搬運越少，但晶片內記憶體用越多。** 這就是 tile size sweep 實驗要量的 trade-off。

### 這是「解法」的原因
Tiling 不改變計算結果，只改變**計算順序**，卻讓**搬運總量**直接除以 4～16 倍。
這是所有矩陣運算加速器（GPU 的 cuBLAS、TPU、LightNobel 的運算單元）都會用的基本手法。

## 2.5 解法二：寬位元與 burst → 提高每次搬運的效率（v1 → v2）

### 白話直覺
v1 雖然減少了趟數，但推車很小，一次只能載 **1 個 float（32 bit）**。
v2 換成大推車，一次載 **16 個 float（512 bit）**，並且 16 個廚師同時切。

### 兩個不同的概念：頻寬 vs 延遲
| 概念 | 意義 | 比喻 |
|---|---|---|
| **頻寬（bandwidth）** | 每秒能搬多少 byte | 高速公路有幾線道 |
| **延遲（latency）** | 從發出請求到拿到第一筆資料要多久 | 從家裡開到倉庫要多久 |

一條 AXI 連接埠（FPGA kernel 連到 HBM 的介面）：
```
頻寬上限 = 位元寬度 × 時脈
  32-bit  × 300 MHz = 1.2 GB/s   （v1）
  512-bit × 300 MHz = 19.2 GB/s  （v2）← 16 倍
```

### Burst（連續搬運）
每次向 HBM 發出請求都要付一次延遲。如果**要的資料在記憶體中是連續的**，可以一次請求、連續拿很多筆，這叫 **burst**。

```
非 burst：請求 → 等 → 拿 1 筆 → 請求 → 等 → 拿 1 筆 → ...   （每筆都付一次延遲）
Burst：   請求 → 等 → 拿 1 筆、1 筆、1 筆、1 筆 ...          （只付一次延遲）
```

**這就是為什麼資料排列（memory layout）很重要：** 我們把資料排成 `[row][col][channel]`，
同一個 token 的 128 個 channel 是**連續的**，所以一次可以 burst 讀完。
v0 在最內層迴圈改變 k，每次跳過 128 個數字（stride = C），**無法形成有效的 burst**，這也是它慢的原因之一。

### Little's Law：要多少資料「在路上」才能用滿頻寬
```
在途資料量 = 頻寬 × 延遲
```
例：頻寬 19.2 GB/s、延遲約 64 cycles（300 MHz 下約 213 ns）
→ 需要約 4 KB 的資料同時在路上，才能讓頻寬不空轉。
**一次只要一小筆、等到了才要下一筆，永遠用不滿頻寬。** 這也說明了 burst 和下一節 double buffering 的重要性。

### 這是「解法」的原因
寬位元讓**每個 cycle 能搬的量**變 16 倍；burst 讓**延遲只付一次**。
兩者結合，同樣的搬運量所需的時間大幅下降。同時，因為一次拿到 16 個數，也能讓 16 個運算單元同時工作，
**運算能力也跟著提高 16 倍**（v2 理論上限 = 16 × 2 × 300 MHz = 9.6 GFLOP/s）。

## 2.6 解法三：Double buffering → 把等待時間藏起來（v2 → v3）

### 白話直覺
v2 的廚師：**搬一批 → 煮一批 → 搬下一批 → 煮下一批**，搬的時候廚師在等。
v3 多準備一個料理台：**廚師煮第 k 批的同時，助手把第 k+1 批搬到另一個料理台**。

```
v2（沒有重疊）：
  時間 ──────────────────────────────────────────────►
  [搬 k=0][ 算 k=0 ][搬 k=1][ 算 k=1 ][搬 k=2][ 算 k=2 ]

v3（double buffering，兩組 buffer 輪流用）：
  [搬 k=0][ 算 k=0 ][ 算 k=1 ][ 算 k=2 ][ 算 k=3 ]
          [搬 k=1]  [搬 k=2]  [搬 k=3]
           ↑ 搬運藏在計算底下
```

### 用實際數字看：v2 的 HLS 報告
每一輪 `loop_k`：
| 步驟 | cycles |
|---|---|
| 載入 a、b（兩個並行） | 141 |
| 計算（mac） | 526 |
| **合計** | **約 671** |

套用 2.1 節的公式：
```
v2（輪流）：T ≈ T_compute + T_memory = 526 + 141 ≈ 671 cycles
v3（重疊）：T ≈ max(T_compute, T_memory) = max(526, 141) ≈ 530 cycles

時間減少 ≈ (671 − 530) ÷ 671 ≈ 21%     → 速度約 1.27 倍
```

### 為什麼上限只有約 21%？
因為**搬運只佔 21% 的時間**。即使把搬運完全藏起來，最多也只能省下這 21%。
這是 **Amdahl's Law** 的例子（見 2.10 節）。

### 延伸觀察：141 cycles 裡大部分是「延遲」
v2 每輪只搬 2 × 64 = 128 個 512-bit word（a、b 各 64 個，兩個 port 並行），
理想上只要約 64 cycles，但報告顯示 141 cycles。
多出的時間大多是 **HBM 的延遲**（HLS 預設假設 64 cycles）和迴圈的啟動成本。
**Double buffering 對付的正是這種「延遲型」的等待**：延遲再長，只要能和計算重疊，就不會影響總時間。

### 這是「解法」的原因
Double buffering 不減少搬運量，也不提高頻寬，而是**改變時間的結構**：
從「相加」變成「取最大值」。當計算和搬運的時間接近時，效果最好（最多快 2 倍）。

## 2.7 解法四：多通道 HBM → 多條路同時搬（cfg 對照實驗）

### U55C 的 HBM 結構
```
16 GB HBM2 = 32 個 pseudo-channel（PC），每個 512 MB、約 14 GB/s
            ┌────┬────┬────┬─────┬────┐
            │PC0 │PC1 │PC2 │ ... │PC31│
            └────┴────┴────┴─────┴────┘
             總頻寬約 460 GB/s（全部同時用的情況下）
```
**單一 PC 的頻寬和容量都不大**，要同時使用多個 PC，才能發揮 HBM 的優勢。

### 本專題的兩種設定
| 設定檔 | a | b | z | 預期效果 |
|---|---|---|---|---|
| `trimul_v2.cfg` | PC 0～7 | PC 8～15 | PC 16～23 | 三份資料走不同的路，互不干擾 |
| `trimul_v2_onebank.cfg` | PC 0 | PC 0 | PC 0 | 三份資料搶同一條路 |

### 這是「解法」的原因
頻寬是「每條路的頻寬 × 同時使用的路數」。讓不同資料走不同的 PC，
等於把公式中的 `頻寬` 乘上倍數；反之，全部擠在同一個 PC 會互相排隊。
這個實驗需要**上板**才看得出效果（HLS 報告無法模擬 HBM 的真實行為）。

## 2.8 解法五：量化 → 讓每筆資料變小（v2 → v4）

### 白話直覺
把食材**壓縮成原本的 1/4 再搬**，搬到後再還原。會有一點失真，但搬運量少了 4 倍。

### INT8 對稱量化的原理
把一組浮點數 `x` 轉成 -127～127 的整數 `q`：
```
scale s = max(|x|) ÷ 127         ← 讓最大的數剛好對應到 127
q       = round(x ÷ s)           ← 四捨五入成整數，存 1 byte
還原     x̂ = s × q
誤差     x − x̂ 落在 [−s/2, +s/2] 之間
```

**誤差的大小取決於 s**：s 越大，每一格越粗，誤差越大。
（在誤差均勻分布的假設下，均方根誤差約為 `s ÷ √12 ≈ 0.29 × s`。）

### 為什麼 outlier 是問題：per-tensor vs per-token
我們的模擬資料：一般的數字大約落在 ±3 以內，但有 1% 的 token 被放大 30 倍（outlier，大約 ±80）。

**Per-tensor（整份資料共用一把尺）：**
```
s = 84 ÷ 127 ≈ 0.66
→ 一般 token（大約 ±3）只能用到約 −4～4 這幾個整數
→ 均方根誤差 ≈ 0.29 × 0.66 ≈ 0.19      ← 相對於數值本身（約 1）將近 20%！
```

**Per-token（每個 token 各自一把尺）：**
```
一般 token：s ≈ 2.8 ÷ 127 ≈ 0.022 → 均方根誤差 ≈ 0.0064（< 1%）
outlier token：s ≈ 0.66，但它自己的數值本來就大，相對誤差一樣很小
```

**結論：** per-tensor 時，**少數 outlier 拖累了其他所有 token**；per-token 讓每個 token 用適合自己的精度。
我們的 C 模擬實測：**per-token 輸出誤差約 1%，per-tensor 約 11%**，與上面的推算方向一致。
這正是 LightNobel「token-wise」量化的核心動機。

### 代價
| 項目 | 代價 |
|---|---|
| 精度 | 約 1% 的相對誤差（per-token） |
| 額外資料 | 每個 token 多存一個 scale（4 bytes / 128 bytes ≈ 3%） |
| 額外運算 | 每次乘加要多乘上 `s_a × s_b`（v4 的 mac 迴圈） |
| 量化本身 | 要先算出每個 token 的最大值（我們在 host 端做，沒有計入 kernel 時間） |

### 算術強度（v4，8×8 tile）
```
資料量 = L³·C·(1/TI + 1/TJ) × 1 byte      （int8）
       + L³·(1/TI + 1/TJ) × 4 bytes        （scale）
AI = 2·L³·C ÷ [L³·(1/TI+1/TJ)·(C + 4)]
   = 2·128 ÷ [(1/4)·132] ≈ 7.8 FLOP/byte     ← 約是 v2 的 3.9 倍
```

### 容量上的好處
| 版本 | a、b 各佔 | z | 總計 |
|---|---|---|---|
| FP32（v2） | L² × 512 B | L² × 512 B | L² × 1,536 B |
| INT8（v4） | L² × 132 B（含 scale） | L² × 512 B（輸出仍是 FP32） | L² × 776 B |

總佔用量**約減半** → 相同記憶體下，L 約可增加 √2 ≈ **1.4 倍**。
（若輸出也量化，才會接近 2 倍，可以當延伸題目。）
> 注意：這是和**我們自己的 FP32 版本**比。LightNobel 的比較基準是 FP16（1.4 節），以 FP16 為基準時 z 只佔 256 B，
> 量化 a、b 的效果會變小；和論文比較時請用 6.10 節的 FP16 數字。

### 這是「解法」的原因
量化同時縮小兩件事：**搬運量**（公式中的分子）和**記憶體佔用**（決定 L 的上限）。
這是唯一一個**直接處理「序列長度受限」**的手法，也是 LightNobel 的核心。

## 2.9 其他常見手法（本專題未實作，但報告中可以提）

| 手法 | 原理 | 代價 | 在 PPM 的例子 |
|---|---|---|---|
| **Chunking（分塊）** | 一次只算一部分，算完就丟 | 時間變長 | AlphaFold2/ESMFold 內建 chunk size 設定 |
| **Recomputation（重算）** | 不存中間值，需要時重新算 | 多花計算 | 訓練時常用的 activation checkpointing |
| **Operator fusion（運算融合）** | 把連續幾個運算合成一個，中間值不寫回記憶體 | 程式較複雜 | LayerNorm + Linear + gating 合併 |
| **低精度浮點（FP16/BF16）** | 每個數用 2 bytes | 範圍或精度下降 | 語言模型部分常用 FP16 |
| **稀疏化** | 跳過接近 0 的值 | 需要不規則存取 | 距離很遠的 (i, j) 對 |

## 2.10 為什麼「效益可能不大」仍然算解法？

### Amdahl's Law
```
整體加速 = 1 ÷ [ (1 − p) + p ÷ s ]

p = 被改善的部分佔原本時間的比例
s = 那部分被加速的倍數
```
例：v3 只改善「等記憶體」那 21%（p = 0.21），即使讓它完全消失（s → ∞）：
```
整體加速 = 1 ÷ (1 − 0.21) ≈ 1.27 倍
```

### 瓶頸轉移
每解決一個瓶頸，**下一個瓶頸就會浮現**：
```
v0：受限於記憶體（AI = 0.25）
 → v1 tiling：搬運量減少 8 倍，但每 cycle 只做 1 次乘加 → 變成受限於運算
 → v2 寬位元 + 16 路平行：運算變 16 倍 → 記憶體延遲佔 21%
 → v3 double buffering：延遲被藏起來 → 又變成受限於運算（16 路）
 → 下一步：增加平行度（例如展開 jj 迴圈）→ 又會回到受限於記憶體 ...
```
**找出每一步的瓶頸在哪、為什麼轉移，本身就是有價值的分析。**
這也是為什麼報告中要畫 roofline：可以看到 kernel 在圖上一步步移動。

### 什麼叫「有解決到問題」
| 問題 | 手法 | 從什麼概念上解決 |
|---|---|---|
| 搬運太多 | Tiling | 利用資料重用，減少重複搬運 |
| 搬運沒效率 | 寬位元、burst | 每次搬更多、延遲只付一次 |
| 等待延遲 | Double buffering | 讓搬運和計算重疊 |
| 頻寬不夠 | 多通道 | 同時使用多條路 |
| 資料太大、放不下 | 量化 | 每筆資料變小，同時降低容量與頻寬需求 |

## 本章小結

- 記住這條公式：`T ≈ T_compute + T_memory`（沒重疊）或 `max(...)`（有重疊），每一招都在縮小其中一項。
- 用**算術強度**判斷 memory-bound 還是 compute-bound；用 **roofline 圖**呈現結果。
- 本專題五個版本的 AI：**0.25 → 2 → 2 → 2 → 約 7.8**（FLOP/byte）。
- Double buffering 的上限由搬運佔比決定（v2 約 21%），這是 Amdahl's Law。
- 量化是唯一同時處理「頻寬」和「容量（序列長度）」的手法，per-token 可以避免 outlier 拖累精度。
