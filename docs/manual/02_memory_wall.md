## 2.1 問題一：記憶體放不下

### 算一算 pair representation 有多大
每個數字用 FP32（4 bytes），每格 128 個數字 → **每格 512 bytes**。

> **精度說明：** 本專題的 kernel 用 FP32（HLS 裡最直接）。LightNobel 的比較基準（ESMFold）是 **FP16**，
> 大小是下表的一半。和論文比較時要用 FP16 當基準，否則量化省下的比例會被誇大
> （INT8 相對 FP32 是 1/4，相對 FP16 只有 1/2；見 9.4 節）。

```
大小 = L × L × 128 × 4 bytes = L² × 512 bytes
```

| L | L² | 一份 pair tensor（FP32） |
|---|---|---|
| 256 | 65,536 | 32 MB |
| 500 | 250,000 | 128 MB |
| 1,000 | 1,000,000 | **512 MB** |
| 2,000 | 4,000,000 | **2 GB** |
| 4,000 | 16,000,000 | **8 GB** |
| 10,000 | 100,000,000 | **51 GB** |

**長度變 2 倍，資料變 4 倍；長度變 10 倍，資料變 100 倍。**

### 實際需要的不只一份
計算一次 Triangle Multiplication 時，同時存在的資料至少有：

| 資料 | 形狀 | 說明 |
|---|---|---|
| 輸入 z | L×L×128 | pair representation 本身 |
| LayerNorm 後的 z | L×L×128 | |
| a、b | 各 L×L×128 | 投影後的兩份 |
| gate（a_g、b_g、g） | 各 L×L×128 | gating 用 |
| 輸出 | L×L×128 | |

粗估**同時有 5～8 份** pair 大小的資料。L = 2000 時，光這一步就可能需要 **10～16 GB**。
再加上 Triangle Attention 的立方級中間值，GPU 記憶體很快就不夠用（Out of Memory, OOM）。

### 為什麼問題出在 activation，不是模型權重
| 類別 | 是什麼 | 大小和 L 的關係 | ESMFold 的量級 |
|---|---|---|---|
| **權重（weights）** | 模型學到的參數 | **固定**，和 L 無關 | ESM-2 3B ＋ folding trunk，FP16 約 **7.90 GB**（論文 Table 1） |
| **Activation** | 計算過程中產生的中間資料 | **隨 L² 甚至 L³ 成長** | L 大時可達數十 GB |

L 小的時候，權重佔大頭；**L 一大，activation 就遠遠超過權重**。
論文 Fig. 4：L = 2,034 時 activation 已經是權重的 **24.15 倍**，需要 **144 GB**，一張 80 GB 的 GPU 放不下。
以 3,364 個胺基酸的 T1169 為例，FP16 的 activation 是 113.49 GB，權重只有 7.90 GB（Table 1）。
所以「把模型變小」幫助有限，真正要處理的是 activation。這正是 LightNobel 的切入點。

### 現在的解法與代價
常見做法是 **chunking（分塊）**：一次只算一部分，算完就丟。
- 優點：記憶體峰值下降。
- 代價：要重複讀資料、無法完全平行，**時間變長**。
- LightNobel 的 GPU 比較對象就有「不分塊」和「分塊（Chunk4）」兩種；分塊後 GPU 能跑更長的序列，但慢很多。

> **小結：** 序列長度被記憶體容量卡住，這就是 LightNobel 標題裡的
> 「*Sequence Length Limitation*」。

## 2.2 問題二：搬資料比計算慢（memory-bound）

### 白話直覺：廚房比喻
- **HBM / DRAM（主記憶體）= 遠處的倉庫**：很大，但來回一趟很花時間。
- **晶片內記憶體（cache、BRAM、shared memory）= 手邊的料理台**：拿取很快，但很小。
- **運算單元 = 廚師**：切菜很快。

如果廚師切一刀，就要等助手跑一趟倉庫拿下一個食材，那廚師大部分時間都在**等**。
**這時候瓶頸是「搬運」，不是「廚師的速度」。** 這就叫 **memory-bound**。
反過來，如果食材都在手邊，只是廚師切不完，就叫 **compute-bound**。

### 用數字判斷：算術強度（Arithmetic Intensity）
```
算術強度 = 運算次數（FLOP） ÷ 從主記憶體搬運的資料量（byte）
```
單位是 FLOP/byte，代表「每搬 1 byte 可以做幾次運算」。**越高越好。**

### 例子：最直白的寫法（我們的 v0）
每算一次 `a × b` 並累加（2 次運算：一次乘、一次加），都要從記憶體讀一個 `a`（4 bytes）和一個 `b`（4 bytes）：
```
算術強度 = 2 FLOP ÷ 8 bytes = 0.25 FLOP/byte
```

### 硬體能提供多少？
| 硬體 | 記憶體頻寬 | 峰值運算能力（FP32） | 平衡點（運算 ÷ 頻寬） |
|---|---|---|---|
| U55C（本專題） | 約 460 GB/s（HBM2） | 取決於設計 | — |
| 一般 GPU（例：A100） | 約 1.5～2 TB/s | 約 19.5 TFLOP/s | 約 10 FLOP/byte |

以 GPU 為例，演算法的算術強度要**超過約 10 FLOP/byte**，才能把運算單元餵飽。
v0 只有 0.25，也就是說**運算單元大約 97% 的時間都在等資料**。

### 那 Triangle Multiplication 本質上是 memory-bound 嗎？
不一定，取決於**怎麼寫**：
- 理論上：總運算量是 `2·L³·C`，但資料只有 `3·L²·C` 個數字。如果每個數字只搬一次，算術強度可以非常高（L 越大越高）。
- 實際上：晶片內的空間放不下整個 L×L×128，只能分批搬，而**分批的方式決定要重複搬幾次**。

**這就是優化的空間所在：** 同樣的計算，搬運方式不同，速度可以差幾十倍。
第 3、4 章會用公式說明每種手法如何減少搬運；第 8 章會看到實際數字（v2 報告中約 21% 的時間在等記憶體）。

## 2.3 記憶體階層：為什麼「搬運」有成本

### 白話直覺
離運算單元越近的記憶體，**越快但越小**；越遠的記憶體，**越大但越慢**。

```
   速度快、容量小                                         速度慢、容量大
 ┌──────────┐   ┌──────────────┐   ┌────────────────┐   ┌─────────────┐
 │ Register │ → │ 晶片內記憶體 │ → │ HBM / DRAM     │ → │ 硬碟 / 網路 │
 │ (FF)     │   │ BRAM / URAM  │   │ (板上主記憶體) │   │             │
 └──────────┘   └──────────────┘   └────────────────┘   └─────────────┘
   1 cycle        1～2 cycles        數十～數百 cycles    非常久
   約 330 KB      U55C 約 43 MB      U55C 16 GB           
```

### U55C 的具體數字
| 層級 | 容量 | 存取延遲 | 備註 |
|---|---|---|---|
| FF（暫存器） | 約 260 萬個 bit（約 330 KB） | 1 cycle | 直接接在運算單元上 |
| BRAM | 4,032 塊 × 18 Kb ≈ 9 MB | 1～2 cycles | 可同時存取很多塊 |
| URAM | 960 塊 × 288 Kb ≈ 35 MB | 1～2 cycles | 比 BRAM 大塊 |
| HBM2 | 16 GB（32 個 pseudo-channel × 512 MB） | 數十～上百 cycles | 總頻寬約 460 GB/s |

**關鍵：** 一份 L = 1000 的 pair tensor 就有 512 MB，晶片內只有約 43 MB，**不可能整份放進來**，一定得分批從 HBM 搬。

## 2.4 一條公式看懂所有優化

一個 kernel 的執行時間，可以粗略拆成「計算」和「搬資料」兩部分：

```
如果計算和搬運「輪流」做（沒有重疊）：
    T  ≈  T_compute + T_memory

如果計算和搬運「同時」做（完全重疊）：
    T  ≈  max(T_compute, T_memory)

其中：
    T_compute = 運算次數 ÷ (每個 cycle 的運算數 × 時脈)
    T_memory  = 搬運量 ÷ 頻寬  +  每次請求的延遲 × 等待次數
```

**每一招優化，都是在縮小其中一項：**

| 手法 | 縮小哪一項 | 對應版本 |
|---|---|---|
| Tiling／資料重用 | `搬運量` ↓ | v1 |
| 寬位元、burst | `頻寬` ↑、`等待次數` ↓ | v2 |
| 平行運算單元 | `每 cycle 運算數` ↑ | v2（16 路）、v4（64 路） |
| Double buffering | 把 `+` 變成 `max` | v3 |
| 多通道 HBM | `頻寬` ↑ | cfg 對照實驗 |
| 量化 | `搬運量` ↓（每筆資料變小） | v4 |

接下來每一節都會回到這條公式。

## 2.5 算術強度與 Roofline 模型

算術強度（AI）在 2.2 節已經介紹過：**每搬 1 byte，能做幾次運算**。Roofline 模型用它來判斷瓶頸在哪裡。

### Roofline 模型
硬體有兩個上限：
1. **運算上限**（每秒最多做幾次運算）：一條水平線。
2. **頻寬上限**（每秒最多搬多少 byte）：AI 越高，同樣頻寬能支撐的運算越多，是一條斜線。

```
效能
(GFLOP/s)
   │                  ┌──────────────────  ← 運算上限（屋頂）
   │                 /
   │                /   ← 頻寬上限（斜率 = 頻寬）
   │               /
   │              /
   │     ● v0    /       ● v2
   │            /
   │           /
   └──────────┴────────────────────────── 算術強度（FLOP/byte，對數軸）
         memory-bound │ compute-bound
                      ↑
                  平衡點（ridge point）
```

- 在平衡點**左邊**：被頻寬限制（memory-bound）→ 要提高 AI 或頻寬。
- 在平衡點**右邊**：被運算能力限制（compute-bound）→ 要增加運算單元。

### 可達效能的公式
```
可達效能 = min( 運算上限 ,  AI × 頻寬 )
```

### 本專題的例子
| 版本 | AI（FLOP/byte） | 說明 |
|---|---|---|
| v0 | 0.25 | 每 2 次運算讀 8 bytes |
| v1、v2、v3（8×8 tile） | 2 | 見 3.1 節推導 |
| v4（INT8，8×8 tile） | 約 7.8 | 見 4.6 節推導 |

**畫 roofline 圖是報告中最重要的圖之一**：可以一眼看出每一招讓 kernel 往哪個方向移動。

## 2.6 Amdahl's Law 與瓶頸轉移

### Amdahl's Law
```
整體加速 = 1 ÷ [ (1 − p) + p ÷ s ]

p = 被改善的部分佔原本時間的比例
s = 那部分被加速的倍數
```
例：v3（double buffering，3.3 節）只改善「等記憶體」那 21%（p = 0.21），即使讓它完全消失（s → ∞）：
```
整體加速 = 1 ÷ (1 − 0.21) ≈ 1.27 倍
```

### 瓶頸轉移
每解決一個瓶頸，**下一個瓶頸就會浮現**。以本專題的各版本為例（各版本的細節在第 3、4 章，這裡先看整體脈絡）：
```
v0：受限於記憶體（AI = 0.25）
 → v1 tiling：搬運量減少 8 倍，但每 cycle 只做 1 次乘加 → 變成受限於運算
 → v2 寬位元 + 16 路平行：運算變 16 倍 → 記憶體延遲佔 21%
 → v3 double buffering：延遲被藏起來 → 又變成受限於運算（16 路）
 → 下一步：增加平行度（例如展開 jj 迴圈）→ 又會回到受限於記憶體 ...
```
**找出每一步的瓶頸在哪、為什麼轉移，本身就是有價值的分析。**
這也是為什麼報告中要畫 roofline：可以看到 kernel 在圖上一步步移動。

## 2.7 解法的地圖：資料表示、資料流、硬體結構

學到這裡，很容易搞不清楚「哪些是軟體優化、哪些是硬體優化」。比較好用的分法是三層：

| 層 | 問的問題 | 例子 | 通常由誰決定 |
|---|---|---|---|
| **① 資料表示** | 每個數**存成什麼格式**？ | FP32、FP16、INT8、INT4、per-token 的尺、outlier 另外存 | 演算法／軟體 |
| **② 資料流（dataflow）** | 資料**怎麼搬、放在哪、什麼順序算**？哪些中間值要存？ | tiling、double buffering、融合、重算、chunking、token-wise attention | 軟體，或做成硬體 |
| **③ 硬體結構** | **誰來算、有多少資源**？ | 運算單元的數量與精度、晶片內記憶體大小、介面寬度、HBM 通道數 | 硬體 |

在 memory-bound 的問題裡，**三層的目標都是減少資料存取**：① 讓每筆資料變小、② 讓搬的次數與存的份數變少、③ 讓搬運更快、晶片內放得更多。

**為什麼在 FPGA 上特別分不清？** 在 GPU 上，硬體是固定的，資料流由程式（軟體）決定。
在 FPGA／ASIC 上，**HLS 的 C++ 迴圈順序會變成電路的資料路徑、陣列大小會變成晶片內記憶體**，資料流的決定直接變成硬體結構，兩層合在一起。

**為什麼需要軟硬體協同設計？** 只改①不一定會變快：LightNobel 指出 GPU 上的 INT4 activation 量化反而比 FP16 慢，
因為 GPU 的運算單元不是為這種格式設計的。所以 LightNobel 同時設計了③（能直接算多種精度的 RMPU、能執行時量化的 VVPU，第 6 章）。

| 手法 | ① 資料表示 | ② 資料流 | ③ 硬體結構 |
|---|---|---|---|
| v1 tiling | | ✅ 一次搬一批、重複使用 | 需要晶片內 buffer |
| v2 寬位元 | | | ✅ 512-bit 介面、16 個運算單元 |
| v3 double buffering | | ✅ 搬運和計算同時做 | 需要兩組 buffer |
| 多通道 HBM | | | ✅ 資料分散到不同通道 |
| v4 INT8／v5 INT4 | ✅ 每個數變小、per-token 尺 | | 需要整數乘法器與解包邏輯 |
| 融合、重算 g（3.5、3.6 節） | | ✅ 中間值不寫回 | 需要把運算串成管線 |
| chunking（GPU） | | ✅ 一次只算一部分 | |
| LightNobel AAQ | ✅ 三組、INT4／INT8、outlier | | |
| LightNobel RMPU／VVPU（第 6 章） | | ✅ 管線、執行時量化 | ✅ 多精度運算單元、排序硬體 |
| LightNobel token-wise attention | | ✅ 不存 L³ 的 score matrix | 需要 scratchpad 與線上最大值追蹤 |

> 一句話：**目標是減少資料存取；軟體決定資料的樣子和搬運順序，硬體決定這些事做起來多快。在 FPGA 上，後兩者是用同一份程式寫出來的。**
