# 第 10 章　專題策略：定位、設計、海報與評審問答

> **本章重點**
> - **定位**：以 LightNobel 的原則為基礎，在現成 FPGA 上實作 Triangle Multiplication，**拆解每一招的貢獻**；融合與執行時量化的原則來自 LightNobel，不是我們的新概念。
> - **策略**三根支柱：逐步拆解（v0～v5）、以論文為依據的融合與量化設計、經過驗證的分析模型與 DSE。
> - **設計**：融合成兩個 kernel（流量約 1/7、容量約 7 份 → 2.5 份）；a、b 屬 C 組 → 先用真實資料驗證，再做 INT4 的 v5。
> - **呈現**：海報對應、30 秒與 3 分鐘講法、評審可能問的問題。

## 10.1 定位：題目、選題理由、和 LightNobel 的關係

### 題目一句話
> 在 FPGA 上實作 PPM 的 pair representation 運算之一（Triangle Multiplication），用逐步優化（v0～v5）與分析模型，
> **量化每一招（包括依論文設定的 token-wise 低位元量化）帶來多少改善、付出多少硬體代價**。

和 LightNobel 的關係：**繼承**它的問題定義、token-wise 量化與管線化（中間值不落地）的原則，**簡化**成單一運算、單一精度，
**新增** FPGA 實作、逐步 ablation、真實資料驗證與分析模型。完整對照見本節後面的「繼承、簡化、新增」，策略細節見 10.2 節。

### 為什麼選 Triangle Multiplication
1. **它是 pair representation 的運算**，直接受 L² 資料量影響；短序列時它佔執行時間最多（36.1%）。
2. 算式簡單（本質是矩陣乘法，沒有 softmax），容易驗證正確性，適合當**第一個**目標。
3. 可以清楚展示「同樣的計算，不同搬運方式」的差異。
4. 量化的效果（per-token vs per-tensor）可以直接呼應 LightNobel。

> **誠實說明：** 長序列時最花時間的是 Triangle Attention（75.9%），不是 Triangle Multiplication。
> Triangle Attention 多了 softmax 和立方大小的 score matrix，需要 FlashAttention 式的 token-wise 做法（LightNobel 的 Sec. 5.4），
> 三週內做不完，列為**未來工作**。本專題的 tiling、寬位元、double buffering、量化和分析模型都可以直接沿用過去。

### 為什麼用 FPGA
- FPGA 可以**自己決定記憶體怎麼接、資料怎麼搬、運算單元擺幾個**，適合展示記憶體優化的每一個細節。
- U55C 有 HBM（多通道高頻寬記憶體），可以做多通道的實驗。
- GPU 上這些細節大多被硬體和驅動程式隱藏，比較難單獨觀察每一招的效果。
- **LightNobel 自己也指出**：GPU 做 activation 量化效率很差（要在執行時量化和反量化，用不到 Tensor Core；W4A4 甚至比 FP16 慢），
  所以才需要專用硬體。FPGA 是「不用流片就能做專用資料路徑」的折衷。

### 我們的貢獻（誠實版）
1. **在 FPGA 上實作 PPM 的 Triangle Multiplication**：搜尋範圍內沒有找到公開的類似實作；LightNobel 本身也只有模擬結果。
2. **把各個記憶體優化手法的貢獻分開量化**（ablation，v0～v5）：論文是整套一起評估，看不出每一招各佔多少。
3. **量化設定有論文依據、也有真實資料驗證**：不是隨便挑一個 bit 數。
4. **經過驗證的分析模型與設計空間探索**：讓結果不只是幾個數據點。

> **注意：融合（中間值不落地）與執行時量化，LightNobel 都已經做了，不是我們的新概念。**
> 我們的角色是「在現成的 FPGA 上實現並拆解這些想法」，不是提出新的原理。
>
> 也不要宣稱「比 LightNobel 好」：兩者平台不同（ASIC vs FPGA）、範圍不同（整個模型 vs 一個運算）。
> 比較好的說法是：「**以 LightNobel 的原則為基礎，在現成硬體上實作其中一個運算，並量化每一招各自的貢獻。**」

## 10.3 融合設計：兩個 kernel 與效益

第 3 章 3.5、3.6 節介紹了融合與重算的原理，這一節是本專題的具體設計。

### 融合後的兩個 kernel
```
Kernel 1：Producer（逐 token 處理）
  讀 z（一次）
    → LayerNorm → 4 個 linear → sigmoid gating → mask
    → token-wise 量化（INT8 或 INT4，per-token scale 當場算出）
  寫出：a、b（低位元 ＋ scale）

Kernel 2：Consumer（einsum ＋ epilogue）
  讀 a、b（tiling 後的 v4／v5 kernel）
    → einsum → LayerNorm_out → linear_z
    → 從 z 重新算 g = sigmoid(linear_g(LayerNorm(z))) → 相乘
  寫出：輸出
```

### 用數字看效果：記憶體流量
以「每個 L² 位置需要搬多少 bytes」計算（FP32、C = 128、每份張量 512 B/L²；einsum 以理想的最少讀取計算）：

| 步驟 | 不融合（每步都讀寫 HBM） | 融合 |
|---|---|---|
| LayerNorm | 讀 z 512 ＋ 寫 z_ln 512 | ─ |
| 5 個 linear | 5 × (讀 512 ＋ 寫 512) = 5,120 | ─ |
| 兩個 gating | 2 × (讀 1,024 ＋ 寫 512) = 3,072 | ─ |
| **Producer** | | 讀 z 512 ＋ 寫 a、b 的 INT8 264 = **776** |
| einsum | 讀 a、b 1,024 ＋ 寫 512 = 1,536 | 讀 a、b 264 |
| LayerNorm_out ＋ linear_z | 2 × 1,024 = 2,048 | ─ |
| × g | 讀 1,024 ＋ 寫 512 = 1,536 | 讀 z 512 ＋ 寫輸出 512 |
| **合計** | **約 14,300 B/L²** | **約 2,060 B/L²（約 1/7）** |

> 這是理想化的估算（einsum 的重複讀取已經在 3.1 節的 tiling 分析過，這裡先不計），
> 目的是說明量級：**融合讓搬運量少了將近一個數量級**。

### 用數字看效果：同時存在的資料量（容量）
| 配置 | 每個 L² 的 bytes | U55C 16 GB 可處理的最大 L |
|---|---|---|
| 典型實作（約 7 份 FP32） | 3,584 | 約 2,190 |
| 融合 ＋ INT8 中間值 | 1,288（z 輸入、輸出各 512，a、b 各 132） | 約 3,650（**約 1.67 倍**） |

公式見 9.4 節。以 LightNobel 的 **FP16** 為基準重算，提升約 **1.52 倍**（9.4 節）。

### 權重小、activation 大
| 項目 | 大小 |
|---|---|
| 5 個 128×128 的 linear 權重（FP32） | 5 × 64 KB = **320 KB** |
| LayerNorm 參數 | 幾 KB |
| U55C 晶片內記憶體 | 約 **43 MB** |
| 一份 pair 張量（L = 2000） | **2 GB** |

**權重可以一直放在晶片內，只有 activation 在流動。** 這和大型語言模型相反（語言模型是權重大、activation 相對小）。

### FPGA 的優勢
- 可以把 LayerNorm → linear → gating → 量化做成**一條管線**，資料一路流過去，不需要中間的 buffer 寫回。
- 每一級的平行度可以各自調整，讓整條管線速度平衡。
- GPU 做融合要手寫 CUDA，而且受限於 shared memory 的大小與 thread 的組織方式；FPGA 則是直接設計資料路徑。

### 硬體成本估算（producer）
每個 token 要做 4 個 128×128 的 linear（a_p、a_g、b_p、b_g）＝ 4 × 16,384 = **65,536 次乘加**。
如果要每 T 個 cycle 處理一個 token，需要 65,536 ÷ T 個乘加器：
| 每個 token 的 cycle 數 T | 需要的乘加器 | FP32 約需 DSP（每個約 5） |
|---|---|---|
| 1,024 | 64 | 約 320 |
| 256 | 256 | 約 1,280 |
| 128 | 512 | 約 2,560 |

U55C 有 9,024 個 DSP。這個表就是**設計空間探索**的一個維度：用多少資源換多少速度。

## 10.4 硬體細節：LayerNorm、量化在源頭完成、該用幾個 bit

### LayerNorm 在硬體上怎麼做
```
mean = Σ x_c / 128
var  = Σ (x_c − mean)² / 128
y_c  = (x_c − mean) / sqrt(var + ε) × γ_c + β_c
```
- 一個 token 只有 128 個數，**整個放在晶片內**，所以可以掃兩次（第一次算平均、第二次算變異數），不會多花 HBM 流量。
- `1 / sqrt(...)` 每個 token 只算一次，成本可以忽略。
- （另一種做法是 **Welford 演算法**，只掃一次就能同時算出平均與變異數，數值也比較穩定。）

### 量化在源頭完成
（4.3 節已說明完整精度只需要在晶片內短暫存在，這裡是它在 producer 中的具體做法。）
per-token 量化需要知道「這個 token 128 個數的最大絕對值」。
在 producer 裡，a 的 128 個數**剛算完、還在暫存器裡**，順便取最大值、算 scale、轉成 INT8，**不需要額外再掃一次資料**。

對比：如果量化是獨立的步驟，要先把 FP32 的 a 寫出去、再讀回來量化，等於多搬了 2 份資料。
**「在資料產生的地方就壓縮」是融合設計的另一個好處。**
這正是 LightNobel 的 VVPU 做的「**執行時量化**」（runtime quantization，Sec. 5.3）；它還多做了 top-k 挑 outlier。

### 該用幾個 bit？論文給的線索
選位元數的一般原則見 4.5 節。依 LightNobel 的分組，a、b 是 linear 之後的值，屬於 **C 組**：平均絕對值約 3.85、平均 outlier 不到 1 個，
論文用 **INT4、不處理 outlier** 就能維持 TM-score。所以：
- 我們的 **INT8 是保守的起點**，誤差應該比論文的設定小。
- **INT4 per-token** 是自然的下一步：a、b 再小一半，容量模型見 9.4 節。
- 真正需要 outlier 處理的是 A 組（接 residual 的 z 本身），那是完整模型才需要處理的部分。

### 先驗證，再實作：兩步驟
**第一步：用真實資料確認假設**（第 1 週，`python/dump_trimul_inputs.py`）。
輸出的 JSON 裡有兩組數字：
| 欄位 | 內容 | 要看什麼 |
|---|---|---|
| `paper_group_C_check` | a、b 每個 token 的平均絕對值、超過 3σ 的值平均有幾個 | 是否接近論文 C 組（3.85、0.64 個）；如果 outlier 明顯更多，a、b 可能需要 outlier 處理 |
| `rel_l2_grid` | INT8／INT4 × per-token／per-channel／per-tensor 的 einsum 誤差 | INT4 per-token 的誤差是否可接受；per-token 是否真的比 per-channel 好 |

這張表也能回答兩個取捨：per-token 是否真的比 per-channel 準（4.2 節，論文的觀察）；
以及值不值得為了硬體省事改用 per-channel（per-channel 的尺在 einsum 裡可以最後乘一次，見 4.4 節）。

**第二步：v5 kernel**（第 2 週）。從 v4 改：
- 一個 512-bit word 剛好放 **128 個 INT4 = 一個完整的 token**（v4 要 2 個 word）。
- 每個 byte 拆成兩個 4-bit 值（要做 sign extension），乘加與 scale 的處理和 v4 相同。
- 預期：讀取量減半、算術強度約加倍；代價是解包的邏輯（LUT）。

如果真實資料顯示 INT4 誤差太大，v5 仍然合成（看硬體代價），結論改成「這個運算需要 INT8」，這同樣是有價值的結果。

### 評審可能問的問題
| 問題 | 回答方向 |
|---|---|
| 為什麼用 FPGA，不用 GPU？ | 可以自訂資料流與記憶體階層，適合拆解每一招；LightNobel 也指出 GPU 做低位元 activation 量化效率很差（W4A4 比 FP16 慢），需要客製硬體，而 FPGA 不用流片就能做到。 |
| HLS 的估計準嗎？ | HLS 是 cycle 級的排程結果；我們用它校正分析模型，並用不同設定交叉驗證（附誤差表）。上板是下一步。 |
| 量化會不會影響預測結構的準確度？ | 我們在真實 ESMFold 的 a、b 上量 einsum 輸出的誤差（10.4）；對結構準確度（TM-score）的影響，論文的設定已驗證變化 < 0.001，我們沒有跑完整模型，列為未來工作。 |
| 和 LightNobel 差在哪？ | LightNobel 是 ASIC（模擬評估）＋ 三組混合精度量化 ＋ 管線化資料流；我們沿用它的原則，在現成 FPGA 上實作其中一個運算，並**把每一招的貢獻拆開量化**（對照表見 10.1 節）。**不要**說融合是我們提出的。 |
| 為什麼只做 Triangle Multiplication？ | 誠實回答：長序列時最花時間的是 Triangle Attention（論文 Fig. 3：75.9%）。Triangle Multiplication 結構最單純（沒有 softmax），適合當第一個目標；tiling、量化、分析模型都能沿用到 Triangle Attention（未來工作）。 |
| 1.5 倍看起來不多？ | L 和記憶體是平方根關係；以 FP16 為基準，融合 ＋ INT8 讓 L 提升約 1.52 倍。論文的 120 倍主要來自不存 score matrix（和不分塊的 GPU 比），量化本身約 1.65 倍，量級一致。 |
| 每個 token 多存一把尺，不是讓資料更多嗎？ | 尺只佔 token 的 1～3%（128 個數才一個浮點數），但每個數從 16 bit 變 8 或 4 bit，整體約變成 1/2～1/4（4.3 節的表）。 |
| 記憶體問題真的解決了嗎？ | 把上限往後推，沒有消除 L² 成長。量化省常數倍；不存中間值（尤其 L³ 的 score matrix）才是大幅延長序列的關鍵（5.4 節）。 |
| 為什麼 a、b 用 INT4（或為什麼還是 INT8）？ | 論文把這類 activation（C 組）用 INT4；我們先用真實資料確認 a、b 的分布接近 C 組，再做 v5。依結果回答「INT4 可行」或「這個運算需要 INT8」。 |
| 你們的貢獻到底是什麼？ | ① 在現成 FPGA 上實作並**拆解每一招**的效果與代價（論文沒有）；② 量化設定有論文依據、有真實資料驗證；③ 經過驗證的分析模型與 DSE。融合與量化的原則來自 LightNobel。 |

### 報告時怎麼講
#### 30 秒版
> 蛋白質結構預測模型裡有一份 L×L×128 的資料，序列越長越放不下。LightNobel 用專用晶片加上 token-wise 量化和管線化資料流解決這個問題，但只有模擬結果。我們在現成的 FPGA 上實作其中的 Triangle Multiplication，**逐步拆解每一種記憶體優化手法各自的貢獻**，並用分析模型找出最佳設計。

#### 3 分鐘版（投影片順序）
1. **問題**：pair representation 隨 L² 成長，Triangle Multiplication 一步就有約 7 份；長序列時 Triangle Attention 更花時間（第 1、2 章）
2. **為什麼難**：memory-bound，roofline 圖（2.5 節）
3. **LightNobel 的解法**與我們的定位（第 5 章、10.1 節）
4. **我們的做法**：逐步優化的 kernel、依論文選的位元數（真實資料驗證）、融合資料流設計（10.3、10.4 節）
5. **結果**：v0～v5 的逐步改善、DSE、可處理的序列長度（FP16 基準）（第 8、9 章）
6. **結論與未來工作**：Triangle Attention、上板、完整的融合 kernel
