# 第 6 章　新策略：逐步拆解、融合與量化設計、分析模型

> **本章重點**
> - 新策略有三根支柱：**① 逐步拆解每一招的貢獻（v0～v4，加上 INT4 的 v5）**、**② 以論文為依據的融合與量化設計**、**③ 經過驗證的分析模型與設計空間探索**。
> - **先說清楚：** 「中間值不落地」和「執行時量化」LightNobel 都已經做了（RMPU → VVPU 管線），不是我們的新概念。我們的貢獻是在現成的 FPGA 上實作，並把每一招的效果拆開量化。
> - **Architectural simulation** 不一定要上板：HLS 合成報告加上校正過的分析模型，就是正統的架構評估方法（LightNobel 也是用模擬器評估）。
> - **融合（fusion）** 的核心：讓中間值不寫回記憶體。以本章的估算，Triangle Multiplication 一步的記憶體流量可以減少約 7 倍，同時存在的資料量從約 7 份降到約 2.5 份。三週內只做**設計＋分析模型**。
> - **位元數有論文依據**：a、b 屬於 LightNobel 的 C 組（INT4、不處理 outlier），所以 INT4 的 v5 是下一步；先用真實資料確認。
> - **分析模型** 讓我們能在幾秒內評估上百種設計，並用 **Pareto 前緣** 挑出最佳設定。
> - 最後一節整理了評審可能會問的問題和回答方向。

## 6.2 Architectural simulation 是什麼？

### 白話直覺
在真正做出晶片之前，先用「**模型**」預測它會有多快、用多少資源。就像蓋大樓之前先做結構計算和模型，而不是直接蓋。

### 評估的四個層級
| 層級 | 方法 | 速度 | 準確度 | 本專題 |
|---|---|---|---|---|
| **分析模型** | 用公式算（cycle = 迴圈次數 × 每次的 cycle） | 毫秒 | 中（要校正） | `make model` |
| **Cycle 級模擬** | 模擬器或 HLS 排程結果 | 分鐘 | 高 | `make hls` 的報告 |
| **RTL 模擬** | 模擬實際的電路 | 小時 | 很高 | `COSIM=1`（可選） |
| **上板量測** | 真的在硬體上跑 | 編譯要數小時 | 最高（真實值） | 第二階段 |

**越上面越快、越能大量探索；越下面越準、但越慢。** 好的做法是：
1. 用下層（HLS 報告）**校正**上層（分析模型）；
2. 用校正後的上層**大量探索**；
3. 挑幾個最好的設定，回到下層**驗證**。

### 學術界也這樣做
架構類論文（包括 LightNobel）大多用自己寫的**cycle 級模擬器**加上**合成工具的面積、功耗估計**來評估，而不是真的做出晶片。
LightNobel 的做法（Sec. 6）：用 Python 寫 cycle-accurate 模擬器，再拿 RTL 模擬的結果交叉驗證，四個資料集的誤差平均 **3.30%**、都在 5% 以內；
面積與功耗用 Synopsys DC（28 nm）和 CACTI 估計，記憶體用 Ramulator 模擬。
我們的對應做法：**分析模型 ↔ HLS 報告**交叉驗證（6.8 節），目標同樣是誤差 10% 以內。
所以「HLS 報告＋分析模型」是正當的 architectural simulation，不是偷懶。

## 6.3 完整的 Triangle Multiplication 長什麼樣子

先前我們只實作了中間的 einsum。實際上 ESMFold 的 Triangle Multiplication（outgoing）是這樣：

```
  z（輸入，L×L×128）
  │
  ├─ LayerNorm ─────────────────► z_ln
  │                                 │
  │        ┌────────────┬───────────┼───────────┬────────────┐
  │        ▼            ▼           ▼           ▼            ▼
  │    linear_a_p   linear_a_g  linear_b_p  linear_b_g    linear_g
  │        │            │ sigmoid   │           │ sigmoid    │ sigmoid
  │        └──── × ─────┘           └──── × ────┘            │
  │              │ × mask                 │ × mask           │
  │              ▼                        ▼                  │
  │              a                        b                  │
  │              └───────── einsum ───────┘                  │
  │                  z_ij = Σ_k a_ik · b_jk                  │
  │                           │                              │
  │                     LayerNorm_out                        │
  │                           │                              │
  │                       linear_z                           │
  │                           └────────────── × ─────────────┘
  │                                           │
  └──────────────────────── + ◄───────────────┘   （residual，在 block 外面加）
                                              ▼
                                            輸出
```

每一個箭頭的結果都是 **L × L × 128** 的張量。
這些 linear 都是「**每個 token 各自**做 128×128 的矩陣乘法」，不同 token 之間互不相干。

### 一般實作會「落地」多少資料？
如果每個運算都是獨立的函式（PyTorch 預設的做法），每一步的結果都要**寫回記憶體**，下一步再讀出來。
同一時間存在的 pair 張量，峰值大約是 **7 份**（z、z_ln、a、b、g、einsum 的結果、各種暫存）。
GPU 上的融合實作分析也是這個量級（見第 6.12 節參考資料）。

## 6.4 Operator fusion（運算融合）的理論

### 白話直覺
**不融合：** 廚師切完洋蔥放回倉庫，另一個廚師再從倉庫拿出來炒。
**融合：** 切完直接下鍋，洋蔥**不回倉庫**。

### 正式說法：producer–consumer
- **Producer**：產生資料的運算（例如 linear_a_p）。
- **Consumer**：使用資料的運算（例如 gating 的乘法）。
- 如果 consumer 在 producer 產生資料後**馬上**用掉，資料就可以留在晶片內（暫存器、BRAM），不必寫回 HBM。
- 這個「產生到使用之間的距離」叫做 **reuse distance**。距離越短，越容易融合。

### 為什麼 Triangle Multiplication 適合融合
LayerNorm、5 個 linear、sigmoid、gating、量化，**全部都是「每個 token 自己算自己的」**：
```
token (i, k) 的 128 個數
   → LayerNorm（只需要這 128 個數的平均與變異數）
   → 5 個 128×128 linear（只需要這個 token ＋ 權重）
   → gating、mask、量化（只需要這個 token）
```
一個 token 的所有處理都可以在晶片內完成，**只有最後的 a、b 需要寫出去**（因為 einsum 需要跨 token 的資料）。

> **和 LightNobel 的關係：** LightNobel 的硬體就是以 token 為單位流動：RMPU 算完 linear，結果以管線方式直接交給 VVPU
> 做 LayerNorm、gating、量化，中間值不寫回外部記憶體（Sec. 5）。本節是**同一個原則**在 Triangle Multiplication 上的具體展開，
> 並額外算出流量與容量各省多少——論文只給整體結果，沒有拆開。

### 融合後的兩個 kernel
```
Kernel 1：Producer（逐 token 處理）
  讀 z（一次）
    → LayerNorm → 4 個 linear → sigmoid gating → mask
    → token-wise 量化（INT8 或 INT4，per-token scale 當場算出）
  寫出：a、b（低位元 ＋ scale）

Kernel 2：Consumer（einsum ＋ epilogue）
  讀 a、b（tiling 後的 v4／v5 kernel）
    → einsum → LayerNorm_out → linear_z
    → 從 z 重新算 g = sigmoid(linear_g(LayerNorm(z))) → 相乘
  寫出：輸出
```

### 用數字看效果：記憶體流量
以「每個 L² 位置需要搬多少 bytes」計算（FP32、C = 128、每份張量 512 B/L²；einsum 以理想的最少讀取計算）：

| 步驟 | 不融合（每步都讀寫 HBM） | 融合 |
|---|---|---|
| LayerNorm | 讀 z 512 ＋ 寫 z_ln 512 | ─ |
| 5 個 linear | 5 × (讀 512 ＋ 寫 512) = 5,120 | ─ |
| 兩個 gating | 2 × (讀 1,024 ＋ 寫 512) = 3,072 | ─ |
| **Producer** | | 讀 z 512 ＋ 寫 a、b 的 INT8 264 = **776** |
| einsum | 讀 a、b 1,024 ＋ 寫 512 = 1,536 | 讀 a、b 264 |
| LayerNorm_out ＋ linear_z | 2 × 1,024 = 2,048 | ─ |
| × g | 讀 1,024 ＋ 寫 512 = 1,536 | 讀 z 512 ＋ 寫輸出 512 |
| **合計** | **約 14,300 B/L²** | **約 2,060 B/L²（約 1/7）** |

> 這是理想化的估算（einsum 的重複讀取已經在第 2 章的 tiling 分析過，這裡先不計），
> 目的是說明量級：**融合讓搬運量少了將近一個數量級**。

### 用數字看效果：同時存在的資料量（容量）
| 配置 | 每個 L² 的 bytes | U55C 16 GB 可處理的最大 L |
|---|---|---|
| 典型實作（約 7 份 FP32） | 3,584 | 約 2,190 |
| 融合 ＋ INT8 中間值 | 1,288（z 輸入、輸出各 512，a、b 各 132） | 約 3,650（**約 1.67 倍**） |

公式見 6.10 節。以 LightNobel 的 **FP16** 為基準重算，提升約 **1.52 倍**（6.10 節）。

## 6.5 用計算換記憶體：為什麼 g 要「重算」

### 問題
g = sigmoid(linear_g(LayerNorm(z))) 在最後才會用到。如果在 producer 算好存起來，就要多存一份 L×L×128。

### 做法：在 consumer 的 epilogue 從 z 重新算
**多花的計算：** 每個輸出位置要多做一次 128×128 的 linear。
```
重算 g 的運算量    = 2 × C² = 2 × 128 × 128 ≈ 32,768 FLOP / 每個輸出位置
einsum 本身的運算量 = 2 × L × C = 256 × L FLOP / 每個輸出位置

比例 = 32,768 ÷ (256 × L) = 128 ÷ L
  L = 256  → 50%
  L = 1024 → 12.5%
  L = 4096 → 約 3%
```
**序列越長，重算的代價越小**，而省下的記憶體（每個 L² 512 bytes）越重要。這正好就是長序列的情境。

### 一般原則：Recomputation
「**不存、需要時再算**」是記憶體不夠時的常見手法（訓練大型模型時的 activation checkpointing 也是同樣的想法）。
判斷值不值得的方法：
```
值得重算 ⇔ 重算的時間 < 存取它所需的時間，或 記憶體容量是瓶頸
```

## 6.6 為什麼這個融合特別適合 FPGA

### 權重小、activation 大
| 項目 | 大小 |
|---|---|
| 5 個 128×128 的 linear 權重（FP32） | 5 × 64 KB = **320 KB** |
| LayerNorm 參數 | 幾 KB |
| U55C 晶片內記憶體 | 約 **43 MB** |
| 一份 pair 張量（L = 2000） | **2 GB** |

**權重可以一直放在晶片內，只有 activation 在流動。** 這和大型語言模型相反（語言模型是權重大、activation 相對小）。

### FPGA 的優勢
- 可以把 LayerNorm → linear → gating → 量化做成**一條管線**，資料一路流過去，不需要中間的 buffer 寫回。
- 每一級的平行度可以各自調整，讓整條管線速度平衡。
- GPU 做融合要手寫 CUDA，而且受限於 shared memory 的大小與 thread 的組織方式；FPGA 則是直接設計資料路徑。

### 硬體成本估算（producer）
每個 token 要做 4 個 128×128 的 linear（a_p、a_g、b_p、b_g）＝ 4 × 16,384 = **65,536 次乘加**。
如果要每 T 個 cycle 處理一個 token，需要 65,536 ÷ T 個乘加器：
| 每個 token 的 cycle 數 T | 需要的乘加器 | FP32 約需 DSP（每個約 5） |
|---|---|---|
| 1,024 | 64 | 約 320 |
| 256 | 256 | 約 1,280 |
| 128 | 512 | 約 2,560 |

U55C 有 9,024 個 DSP。這個表就是**設計空間探索**的一個維度：用多少資源換多少速度。

## 6.7 硬體細節：LayerNorm、量化在源頭完成、該用幾個 bit

### LayerNorm 在硬體上怎麼做
```
mean = Σ x_c / 128
var  = Σ (x_c − mean)² / 128
y_c  = (x_c − mean) / sqrt(var + ε) × γ_c + β_c
```
- 一個 token 只有 128 個數，**整個放在晶片內**，所以可以掃兩次（第一次算平均、第二次算變異數），不會多花 HBM 流量。
- `1 / sqrt(...)` 每個 token 只算一次，成本可以忽略。
- （另一種做法是 **Welford 演算法**，只掃一次就能同時算出平均與變異數，數值也比較穩定。）

### 量化在源頭完成
per-token 量化需要知道「這個 token 128 個數的最大絕對值」。
在 producer 裡，a 的 128 個數**剛算完、還在暫存器裡**，順便取最大值、算 scale、轉成 INT8，**不需要額外再掃一次資料**。

對比：如果量化是獨立的步驟，要先把 FP32 的 a 寫出去、再讀回來量化，等於多搬了 2 份資料。
**「在資料產生的地方就壓縮」是融合設計的另一個好處。**
這正是 LightNobel 的 VVPU 做的「**執行時量化**」（runtime quantization，Sec. 5.3）；它還多做了 top-k 挑 outlier。

### 該用幾個 bit？論文給的線索
依 LightNobel 的分組，a、b 是 linear 之後的值，屬於 **C 組**：平均絕對值約 3.85、平均 outlier 不到 1 個，
論文用 **INT4、不處理 outlier** 就能維持 TM-score。所以：
- 我們的 **INT8 是保守的起點**，誤差應該比論文的設定小。
- **INT4 per-token** 是自然的下一步：a、b 再小一半，容量模型見 6.10 節。
- 真正需要 outlier 處理的是 A 組（接 residual 的 z 本身），那是完整模型才需要處理的部分。

### 先驗證，再實作：兩步驟
**第一步：用真實資料確認假設**（第 1 週，`python/dump_trimul_inputs.py`）。
輸出的 JSON 裡有兩組數字：
| 欄位 | 內容 | 要看什麼 |
|---|---|---|
| `paper_group_C_check` | a、b 每個 token 的平均絕對值、超過 3σ 的值平均有幾個 | 是否接近論文 C 組（3.85、0.64 個）；如果 outlier 明顯更多，a、b 可能需要 outlier 處理 |
| `rel_l2_grid` | INT8／INT4 × per-token／per-channel／per-tensor 的 einsum 誤差 | INT4 per-token 的誤差是否可接受；per-token 是否真的比 per-channel 好 |

per-channel（每個 channel 一把尺）是 LLM 常用的做法。論文認為 PPM 的 activation「channel 之間差異小、token 之間差異大」，
所以 per-token 比較適合；這張表可以直接驗證這個說法在 Triangle Multiplication 上是否成立。

**第二步：v5 kernel**（第 2 週）。從 v4 改：
- 一個 512-bit word 剛好放 **128 個 INT4 = 一個完整的 token**（v4 要 2 個 word）。
- 每個 byte 拆成兩個 4-bit 值（要做 sign extension），乘加與 scale 的處理和 v4 相同。
- 預期：讀取量減半、算術強度約加倍；代價是解包的邏輯（LUT）。

如果真實資料顯示 INT4 誤差太大，v5 仍然合成（看硬體代價），結論改成「這個運算需要 INT8」，這同樣是有價值的結果。

## 6.8 分析模型：用公式預測硬體表現

### 為什麼要做模型
1. **快**：一次 HLS 合成要幾分鐘到幾十分鐘，模型只要幾毫秒 → 可以探索上百種設定。
2. **能解釋**：公式直接告訴你時間花在哪裡。
3. **能預測**：還沒實作的設計（例如融合架構）也能先估計。

### 模型的結構（以 v2 為例）
```
總 cycle    = tile 數 × 每個 tile 的 cycle
tile 數     = (L / TI) × (L / TJ)
每個 tile   = init ＋ L × loop_k ＋ store ＋ 少量額外
loop_k      = load ＋ mac ＋ 4                     （v2：輪流做）
            = max(load, mac) ＋ 4                  （v3：重疊）
load        = max(TI, TJ) × C/16 ＋ 77             （77 = HBM 延遲與啟動成本）
mac         = TI × TJ × C/16 ＋ 14                 （14 = pipeline 深度）
```

### 校正（calibration）
公式裡有一些**無法事先知道的常數**（例如 77、14），要從實際的 HLS 報告反推：
| 報告中的數字 | 公式 | 反推出的常數 |
|---|---|---|
| load = 141 | 8 × 8 ＋ overhead | overhead = **77** |
| mac = 526 | 8 × 8 × 8 ＋ depth | depth = **14** |
| store = 586 | 512 ＋ overhead | overhead = **74** |

### 驗證（validation）
用校正好的模型預測 v2：**177,029,120 cycles**；HLS 報告：**177,029,185 cycles** → 誤差 < 0.01%。

⚠️ 注意：用同一份報告校正又驗證，當然會很準。**真正的驗證**是：
- 用 v2（8×8）校正，去預測 **v2 的 16×16、32×32**（`make hls-sweep` 的結果）；
- 以及預測 **v3、v4**（`make hls-all` 的結果）。
如果誤差在 10% 以內，模型就可信；誤差大的話，要找出是哪一項公式沒考慮到，這個過程本身也是很好的報告內容。

### 模型的限制（報告中要誠實寫出）
- HLS 報告本身也是估計值，實際上板可能因為 HBM 的真實延遲、時脈而不同。
- 資源（DSP、BRAM）目前是粗估，只能看趨勢。
- 沒有模擬 HBM 的頻寬競爭（多個 port 搶同一個通道的情況）。

## 6.9 設計空間探索（DSE）與 Pareto 前緣

### 設計空間
所有「可以調的旋鈕」組成的空間：
| 旋鈕 | 可選值 |
|---|---|
| 版本 | v2、v3、v4、v5、融合 |
| Tile 大小 | 4、8、16、32 |
| 平行度 | 16、32、64 lane |
| 精度 | FP32、INT8、INT4（v5） |

組合起來有上百種，每種都去合成太慢，所以用模型快速評估。

### Pareto 前緣
通常沒有「各方面都最好」的設計：快的用比較多資源、省資源的比較慢。
**Pareto 最佳**：找不到另一個設計在**所有指標都一樣好、而且至少一項更好**。

```
 cycle 數
 （越低越好）
   │  ●  v2@4
   │
   │        ● v2@8
   │                    ● v2@32       ← 被 v3@16 支配（更慢、用更多 BRAM）
   │     ○ v3@8
   │          ○ v3@16
   │                 ○ v4@16
   │                          ○ v4@32
   └──────────────────────────────────── BRAM 用量（越低越好）
   ○ = Pareto 最佳（連起來就是 Pareto 前緣）
```

`make model` 目前的結果（模型值，v4 常數待校正）：
**Pareto 最佳：v2@8×8、v3@8×8、v3@16×16、v4@16×16、v4@32×32**

### 怎麼選
- 資源很緊 → 選前緣左端（省資源）。
- 要最快 → 選前緣右端。
- 報告中可以說：「我們選 X，因為它在前緣的『膝點』（再多花資源，速度提升就很有限）」。

## 6.10 容量模型：最多能處理多長的序列

### 公式
```
需要的記憶體 = L² × (每個 L² 位置的 bytes)
最大 L      = sqrt(可用記憶體 ÷ 每個 L² 位置的 bytes)
```

### 例子（U55C 的 16 GB HBM）
| 配置 | bytes / L² | 最大 L |
|---|---|---|
| 典型實作（約 7 份 FP32） | 7 × 512 = 3,584 | sqrt(16 × 2³⁰ ÷ 3,584) ≈ **2,190** |
| 融合 ＋ INT8 中間值 | 2 × 512 ＋ 2 × 132 = 1,288 | ≈ **3,650** |

**上表以 FP32 為基準，會誇大效果。** LightNobel 的比較基準（ESMFold）是 **FP16**，換成 FP16 重算（`make model` 已加入這幾列）：

| 配置（FP16 基準） | bytes / L² | 最大 L | 相對 |
|---|---|---|---|
| 典型實作（約 7 份 FP16） | 7 × 256 = 1,792 | ≈ **3,096** | 1.00× |
| 融合 ＋ FP16 z ＋ INT8 a、b | 2 × 256 ＋ 2 × 132 = 776 | ≈ **4,705** | **1.52×** |
| 融合 ＋ FP16 z ＋ INT4 a、b（延伸） | 2 × 256 ＋ 2 × 68 = 648 | ≈ **5,148** | 1.66× |

報告時**用 FP16 基準的 1.52 倍**比較誠實；FP32 基準的 1.67 倍只能說「相對於我們自己的 FP32 實作」。

### 為什麼只提升 1.67 倍，不是 7 倍？
因為記憶體和 L² 成正比，**L 只和記憶體的平方根成正比**：
```
L 的提升 = sqrt(記憶體減少的倍數) = sqrt(3,584 ÷ 1,288) = sqrt(2.78) ≈ 1.67
```
要讓 L 變 2 倍，記憶體要降到 1/4；要變 10 倍，記憶體要降到 1/100。
這也是為什麼 LightNobel 要把 peak memory 降低到上百倍，才能大幅延長序列。

> **看懂論文的 120 倍：** 120.05 倍是和「**不分塊**」的 GPU 比（GPU 會存下整個立方大小的 score matrix）；
> 和「**有分塊**」的 GPU 比只有 **1.26～5.05 倍**。很大一部分的節省來自 token-wise 的 attention（不存 score matrix），
> 量化本身（AAQ）在同樣資料流下是 121.39 GB → 73.50 GB，約 **1.65 倍**（Table 1）。
> 所以我們的 1.5 倍左右，和論文中「量化 ＋ 不落地」這部分的量級是一致的，並不是做得特別差。

### 評審可能問的問題
| 問題 | 回答方向 |
|---|---|
| 為什麼用 FPGA，不用 GPU？ | 可以自訂資料流與記憶體階層，適合拆解每一招；LightNobel 也指出 GPU 做低位元 activation 量化效率很差（W4A4 比 FP16 慢），需要客製硬體，而 FPGA 不用流片就能做到。 |
| HLS 的估計準嗎？ | HLS 是 cycle 級的排程結果；我們用它校正分析模型，並用不同設定交叉驗證（附誤差表）。上板是下一步。 |
| 量化會不會影響預測結構的準確度？ | 我們在真實 ESMFold 的 a、b 上量 einsum 輸出的誤差（6.7）；對結構準確度（TM-score）的影響，論文的設定已驗證變化 < 0.001，我們沒有跑完整模型，列為未來工作。 |
| 和 LightNobel 差在哪？ | LightNobel 是 ASIC（模擬評估）＋ 三組混合精度量化 ＋ 管線化資料流；我們沿用它的原則，在現成 FPGA 上實作其中一個運算，並**把每一招的貢獻拆開量化**（對照表見「速覽」第 6 節）。**不要**說融合是我們提出的。 |
| 為什麼只做 Triangle Multiplication？ | 誠實回答：長序列時最花時間的是 Triangle Attention（論文 Fig. 3：75.9%）。Triangle Multiplication 結構最單純（沒有 softmax），適合當第一個目標；tiling、量化、分析模型都能沿用到 Triangle Attention（未來工作）。 |
| 1.5 倍看起來不多？ | L 和記憶體是平方根關係；以 FP16 為基準，融合 ＋ INT8 讓 L 提升約 1.52 倍。論文的 120 倍主要來自不存 score matrix（和不分塊的 GPU 比），量化本身約 1.65 倍，量級一致。 |
| 為什麼 a、b 用 INT4（或為什麼還是 INT8）？ | 論文把這類 activation（C 組）用 INT4；我們先用真實資料確認 a、b 的分布接近 C 組，再做 v5。依結果回答「INT4 可行」或「這個運算需要 INT8」。 |
| 你們的貢獻到底是什麼？ | ① 在現成 FPGA 上實作並**拆解每一招**的效果與代價（論文沒有）；② 量化設定有論文依據、有真實資料驗證；③ 經過驗證的分析模型與 DSE。融合與量化的原則來自 LightNobel。 |

## 本章小結
- **新策略 = 逐步拆解（v0～v5）＋ 以論文為依據的融合與量化設計 ＋ 分析模型與 DSE。** 不需要板子就能完成 architectural simulation。
- **融合**：Triangle Multiplication 裡除了 einsum，全部都是逐 token 的運算，可以在晶片內一路做完；記憶體流量估計減少約 7 倍。
- **重算 g**：用 128/L 比例的額外計算，換掉一整份 pair 張量，序列越長越划算。
- **量化在源頭完成**：在 producer 裡順便算 scale，不必多掃一次資料（即 LightNobel VVPU 的執行時量化）。
- **位元數**：a、b 屬 C 組 → 先用真實資料驗證，再做 INT4 的 v5。
- **分析模型**：用 HLS 報告校正常數，再用不同設定驗證；用 Pareto 前緣挑設計。
- **容量**：L 和記憶體是平方根關係。以 FP32 為基準 L 提升約 1.67 倍；**以論文的 FP16 為基準約 1.52 倍**，報告用後者。
