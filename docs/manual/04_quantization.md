# 第 4 章　量化：讓每筆資料變小

> **本章重點**
> - 先認識 **INT（二補數）與 FP（科學記號）** 在 bit 上的格式。
> - 量化是**壓縮**，不是標準化：尺（scale）跟著資料存下來，用的時候乘回去。
> - **per-token** 為什麼比 per-tensor 準；per-channel 又是什麼。
> - 尺的**成本與格式**：每 128 個數多一個浮點數，只佔 1～3%；完整精度只在晶片內存在一下子。
> - 尺在**什麼時候乘**，取決於加總的方向——這直接影響硬體設計。
> - 位元數怎麼選，以及量化的代價、算術強度與容量上的好處。

---

## 4.1 量化的原理：壓縮，不是標準化

### 白話直覺
把食材**壓縮成原本的 1/4 再搬**，搬到後再還原。會有一點失真，但搬運量少了 4 倍。
（1/4 是相對我們的 FP32；LightNobel 的基準是 FP16，INT8 相對 FP16 是 1/2、INT4 是 1/4。）

### 先認識格式：INT 與 FP 在 bit 上長什麼樣子
**整數（INT）用二補數：** 最高位代表負的 2 的次方，其他位代表正的。
```
INT8：  b7    b6   b5   b4   b3   b2   b1   b0
權重： −128   64   32   16    8    4    2    1

 5   = 0000 0101                    （4 + 1）
−5   = 1111 1011                    （−128 + 64 + 32 + 16 + 8 + 2 + 1）
−93  = 1010 0011                    （−128 + 32 + 2 + 1）
負數的快速算法：正數的 bit 全部反轉再加 1（0000 0101 → 1111 1010 → 1111 1011）
```
| 格式 | 範圍 | 例子 |
|---|---|---|
| INT4 | −8～7 | 5 = `0101`、−5 = `1011` |
| INT8 | −128～127 | −93 = `1010 0011` |
| INT16 | −32,768～32,767 | 1234 = `0000 0100 1101 0010` |

格子**等間距**（相鄰的值永遠差 1），硬體直接對 bit 運算，很簡單。
（對稱量化只用 −127～127 或 −7～7，不用最負的那個值；而且量化後存的 q 不是真正的值，真正的值是 `尺 × q`。）

**浮點數（FP）是科學記號：** bit 分成正負號、次方、有效數字三段：`值 = (−1)^正負號 × 1.有效數字 × 2^(次方 − 偏移量)`。
```
6.5 = 110.1（二進位）= 1.101 × 2²

FP32（1 + 8 + 23 bit，偏移量 127）：
正負號   次方（8 bit）         有效數字（23 bit）
  0      10000001             10100000000000000000000        = 0x40D00000
 正數    129 − 127 = 2        「1.」後面的 101（開頭的 1 不存，叫隱藏位）

−6.5 只有正負號不同：1 10000001 101000…（0xC0D00000）
0.000787 ≈ 1.612 × 2⁻¹¹：0 01110100 10011100100111010101101（116 − 127 = −11）
```
| 格式 | 正負號 | 次方 | 有效數字 | 最大值 | 大約精度 | 6.5 的樣子 |
|---|---|---|---|---|---|---|
| FP32 | 1 | 8 | 23 | 約 3.4 × 10³⁸ | 約 7 位十進位 | `0 10000001 10100000000000000000000` |
| FP16 | 1 | 5 | 10 | 65,504 | 約 3 位 | `0 10001 1010000000` |
| BF16 | 1 | 8 | 7 | 約 3.4 × 10³⁸ | 約 2～3 位 | `0 10000001 1010000` |

格子**不等間距**：靠近 0 很密、越大越疏，所以能同時表示很大和很小的數。
FP16 最小的正規數約 6 × 10⁻⁵（4.3 節提醒尺太小時 FP16 會不準）；BF16 是把 FP32 的後 16 bit 砍掉，範圍和 FP32 一樣、精度較差。

**對硬體的意義：** 整數乘法直接相乘；浮點乘法要「次方相加 ＋ 有效數字相乘 ＋ 正規化 ＋ 處理 0、無限大、NaN」，成本大很多。
所以量化**不只讓資料變小，也讓運算單元變簡單**：LightNobel 的 RMPU 全是整數乘法器（6.4 節），我們的 v4 也是 INT8 相乘、最後才乘 FP32 的尺。

### INT8 對稱量化的原理
把一組浮點數 `x` 轉成 -127～127 的整數 `q`：
```
scale s = max(|x|) ÷ 127         ← 讓最大的數剛好對應到 127
q       = round(x ÷ s)           ← 四捨五入成整數，存 1 byte
還原     x̂ = s × q
誤差     x − x̂ 落在 [−s/2, +s/2] 之間
```

**誤差的大小取決於 s**：s 越大，每一格越粗，誤差越大。
（在誤差均勻分布的假設下，均方根誤差約為 `s ÷ √12 ≈ 0.29 × s`。）

### 量化是「壓縮」，不是「標準化」
初學者常見的疑問：「每個 token 用自己的尺，不就變成每個 token 只跟自己比的『標準分數』了嗎？」

不會。關鍵是**尺（scale）會跟著資料一起存下來**，用的時候乘回去（`x̂ = s × q`），數值就**回到原本的大小**，
token 之間照樣可以比較、一起運算。量化只是**換一個比較省空間的記法**；
真正會改變數值意義的是 LayerNorm 那種「標準化」，兩者不要搞混。

比喻：量螞蟻用公釐尺、量房子用公尺尺，再在旁邊註明單位。每個東西用自己的尺，換算回來仍然能互相比較，而且都量得很準。
如果全部都用公尺尺（per-tensor），房子很準，但螞蟻只能記成「0 公尺」。

另外，scale **不是從樣本「估計」出來的**，而是直接取這 128 個數的最大絕對值，精確、不會估錯。
一把尺只需要涵蓋它要記錄的那些數；**涵蓋的範圍越小，刻度越細，誤差越小**。這正是 per-token 準確的原因。

### 數字例子：兩個 token 一大一小
（為了簡化，每個 token 只看 3 個數。）
```
token 1：[ 0.10, −0.05, 0.08 ]      ← 數值很小
token 2：[ 30,   −12,   25   ]      ← 數值很大（outlier token）
```
**Per-tensor（兩個 token 共用一把尺）：**
```
s = 30 ÷ 127 ≈ 0.236
token 1： 0.10 ÷ 0.236 =  0.42 → 0
         −0.05 ÷ 0.236 = −0.21 → 0
          0.08 ÷ 0.236 =  0.34 → 0
還原：[0, 0, 0]                        ← token 1 的資訊全部消失
```
**Per-token（每個 token 用自己的尺）：**
```
token 1：s₁ = 0.10 ÷ 127 ≈ 0.000787
         q  = [127, −64, 102]
         還原 = [0.100, −0.0504, 0.0803]   ← 幾乎完全一樣
token 2：s₂ = 30 ÷ 127 ≈ 0.236，還原誤差也很小
```
代價只是每 128 個數多存一個 scale（4 bytes，約 3%）。

## 4.2 Per-token、per-tensor、per-channel

### 為什麼 outlier 是問題：per-tensor vs per-token
我們的模擬資料：一般的數字大約落在 ±3 以內，但有 1% 的 token 被放大 30 倍（outlier，大約 ±80）。

**Per-tensor（整份資料共用一把尺）：**
```
s = 84 ÷ 127 ≈ 0.66
→ 一般 token（大約 ±3）只能用到約 −4～4 這幾個整數
→ 均方根誤差 ≈ 0.29 × 0.66 ≈ 0.19      ← 相對於數值本身（約 1）將近 20%！
```

**Per-token（每個 token 各自一把尺）：**
```
一般 token：s ≈ 2.8 ÷ 127 ≈ 0.022 → 均方根誤差 ≈ 0.0064（< 1%）
outlier token：s ≈ 0.66，但它自己的數值本來就大，相對誤差一樣很小
```

**結論：** per-tensor 時，**少數 outlier 拖累了其他所有 token**；per-token 讓每個 token 用適合自己的精度。
我們的 C 模擬實測：**per-token 輸出誤差約 1%，per-tensor 約 11%**，與上面的推算方向一致。
這正是 LightNobel「token-wise」量化的核心動機。

### 那 per-channel 呢？
LLM 常用 **per-channel**（每個 channel 一把尺），因為 LLM 的 activation 是「某幾個 channel 特別大」。
LightNobel 觀察到 PPM 相反：**channel 之間差異小、token 之間差異大**，outlier 集中在特定位置的 token（5.2 節），
所以選 per-token。另一個好處是硬體：linear、LayerNorm 都是逐 token 做的，per-token 的 scale 剛好跟著 token 走，
per-channel 則要在每個 token 內逐一反量化。第 10 章 10.4 節會用真實資料比較這三種粒度。

## 4.3 尺的成本與格式

### 加了尺，資料不是更多嗎？
尺是加上去了，但**每個數字變小的幅度遠大於多出來的那把尺**。以一個 token（128 個數）為例：

| 存法 | 128 個數本身 | 額外資料 | 一個 token 總共 | 相對 FP16 |
|---|---|---|---|---|
| FP32（我們的 v2） | 512 B | 無 | 512 B | 200% |
| **FP16（論文的基準）** | 256 B | 無 | **256 B** | 100% |
| INT8 ＋ 尺（我們的 v4） | 128 B | scale 4 B | 132 B | 約 52% |
| INT4 ＋ 尺（論文的 C 組） | 64 B | scale 2～4 B | 約 68 B | 約 27% |
| INT8 ＋ 4 個 outlier ＋ 尺（論文的 A 組，估算） | 128 B | outlier 8 B ＋ 位置約 4 B ＋ scale 2～4 B | 約 144 B | 約 56% |

**尺只佔整個 token 的 1～3%**：128 個數才多一個。比喻：一箱 128 顆蘋果原本每顆用大盒子裝，
現在改用小盒子，只在箱子外面多貼一張「換算倍率」的標籤。

### 尺本身用什麼格式存？
**尺是用浮點數存的**（FP16 或 FP32），不是用幾個 bit 的整數。我們的 v4 用 **FP32（4 bytes）**，見 `trimul_v4.cpp` 的 `sa`、`sb`；
LightNobel 的論文沒有寫明尺的位元數，只說每個 token 的尺和資料存在一起（Fig. 7 的排列：inlier → outlier → 尺 → outlier 位置）。

**「0.000787 小數點後這麼多位，不是要很多 bit 嗎？」不會，這正是浮點數的設計。**
浮點數就像科學記號，只存「有效數字」和「次方」：
```
0.000787 = 7.87 × 10⁻⁴               （科學記號：只要記 787 和 −4）
         = 1.612 × 2⁻¹¹              （電腦用 2 的次方）

FP16 的 16 個 bit：1 個正負號 ＋ 5 個 bit 存次方（−11）＋ 10 個 bit 存有效數字（1.612）
```
數字多小都一樣：小數點後有幾個 0 只影響「次方」，而次方只佔幾個 bit。

**尺存起來的誤差可以忽略：** FP16 的相對誤差最多約 2⁻¹¹ ≈ 0.05%；
量化本身每一格的誤差最多是最大值的 0.5 ÷ 127 ≈ 0.4%，大了將近 10 倍。
（小提醒：FP16 能正常表示的最小值約 6×10⁻⁵，token 的值如果都非常小，尺會小到 FP16 表示不準，所以很多實作用 FP32 或 BF16 存尺。我們用 FP32，沒有這個問題。）

### 算尺的時候不是要先有完整精度的資料嗎？
要，但**完整精度的資料只在晶片內存在一下子，而且一次只有一個 token**：
```
算出 token (i, j) 的 128 個數（完整精度，256～512 B，放在晶片內）
   → 取最大值、算出尺、轉成 INT8／INT4
   → 只把壓縮後的版本寫進 HBM
   → 換下一個 token
```
真正佔記憶體的 L×L 個 token，**全部都是壓縮後的版本**；完整精度的資料從來不會整份存下來（10.4 節「量化在源頭完成」）。

## 4.4 尺在什麼時候乘？

**情況一：linear（一個 token × 權重矩陣）。** 加總沿著**同一個 token** 的 128 個 channel，這 128 個數共用一把尺，
所以可以把尺提出來：整數先乘加完，**最後只乘一次尺**。
```
y = Σ_c (s_x × q_x[c]) × W[c] = s_x × Σ_c q_x[c] × W[c]
```
LightNobel 的 linear 就是這樣做（Sec. 8.3：「最後才乘一次尺，省掉重複的反量化」）。

**情況二：Triangle Multiplication 的 einsum（本專題的 kernel）。** 加總沿著 **k**，也就是跨越不同的 token (i, k)。
每個 k 是不同的 token，**尺都不一樣，不能提出來**：
```
z[i][j][c] = Σ_k (s_a[i][k] × q_a[i][k][c]) × (s_b[j][k] × q_b[j][k][c])
           = Σ_k (s_a[i][k] × s_b[j][k]) × (q_a × q_b)      ← 每一項都要乘自己的尺
```
所以 v4 的 `mac` 迴圈每個 k 先算一次 `s = s_a × s_b`，再讓 64 個 lane 的整數乘積都乘上 s 才累加。
這就是 v4 的代價表中「每次乘加要多乘上 `s_a × s_b`」的原因，也讓 v4 需要較多的 DSP。

**數字例子：只看一個 channel，k 只有兩項。** 每個 token 用 2 個 channel 代表（[c0, c1]），看 c1 的結果。
```
a[i][0] = [0.10, −0.04]   a[i][1] = [2.0, 0.9]      ← 一小一大
b[j][0] = [3.0,  1.2 ]    b[j][1] = [−0.4, 0.3]
正確答案（c1）：(−0.04)(1.2) + (0.9)(0.3) = −0.048 + 0.270 = 0.222
```
v4 的 mac 迴圈實際做的事：

| k | s_a（= max ÷ 127） | q_a | s_b | q_b | 整數乘積（c1） | s = s_a × s_b | 乘上 s |
|---|---|---|---|---|---|---|---|
| 0 | 0.000787 | [127, −51] | 0.02362 | [127, 51] | −51 × 51 = −2,601 | 1.860e−5 | −0.04838 |
| 1 | 0.01575 | [127, 57] | 0.00315 | [−127, 95] | 57 × 95 = 5,415 | 4.960e−5 | 0.26858 |

```
累加：−0.04838 + 0.26858 = 0.22021     （誤差 0.8%）
```
**如果錯誤地把尺提出來**（整數先加完，最後乘 k=0 的尺）：
```
(−2,601 + 5,415) × 1.860e−5 = 0.0523     ← 差了 4 倍多
```
兩個 k 的尺差了將近 3 倍（1.86e−5 vs 4.96e−5），不能共用。這就是 v4 每個 k 都要先乘自己的 s 再累加的原因。

> **給硬體設計的觀察：** 如果改用 per-channel 的尺（每個 c 一把），尺在 k 方向上是固定的，就可以提出來、最後乘一次，
> 硬體比較省；但精度可能比較差。這是「精度 vs 硬體成本」的取捨，10.4 節的真實資料誤差表（`rel_l2_grid`）可以幫忙判斷。

## 4.5 位元數怎麼選

INT4 只有 −7～7 共 15 個整數，scale 是 INT8 的約 18 倍，誤差也大約大 18 倍。
所以 INT4 只適合**數值分布平均、outlier 少**的資料。LightNobel 就是依這個原則分組：
outlier 多的 A 組用 INT8，outlier 少的 C 組用 INT4（5.3 節）。

**有 outlier 又想用低位元怎麼辦？** 常見的做法是**混合精度**：把每個 token 裡少數幾個特別大的值挑出來，
用高精度（例如 INT16）另外存，其餘的值用低位元。這樣尺只需要涵蓋「一般的值」，刻度就細了。
代價是要多存 outlier 的值和位置，而且挑出最大的幾個值（top-k）需要排序。
LightNobel 的 A、B 組就是這樣做的（5.3 節），它用什麼硬體挑 top-k，見 6.5.2 節。

**怎麼決定？** 用實驗掃過「位元數 × outlier 數量」，看精度和資料量的取捨，選最有效率的點。
LightNobel 就是用這種設計空間探索決定三組的設定（5.3 節）；本專題會用真實資料做同樣的事（10.4 節）。

## 4.6 代價、算術強度與容量

### 代價
| 項目 | 代價 |
|---|---|
| 精度 | 約 1% 的相對誤差（per-token） |
| 額外資料 | 每個 token 多存一個 scale（4 bytes / 128 bytes ≈ 3%） |
| 額外運算 | 每次乘加要多乘上 `s_a × s_b`（v4 的 mac 迴圈） |
| 量化本身 | 要先算出每個 token 的最大值（我們在 host 端做，沒有計入 kernel 時間；LightNobel 在硬體裡「執行時」做，見 10.4 節） |

### 算術強度（v4，8×8 tile）
```
資料量 = L³·C·(1/TI + 1/TJ) × 1 byte      （int8）
       + L³·(1/TI + 1/TJ) × 4 bytes        （scale）
AI = 2·L³·C ÷ [L³·(1/TI+1/TJ)·(C + 4)]
   = 2·128 ÷ [(1/4)·132] ≈ 7.8 FLOP/byte     ← 約是 v2 的 3.9 倍
```

### 容量上的好處
| 版本 | a、b 各佔 | z | 總計 |
|---|---|---|---|
| FP32（v2） | L² × 512 B | L² × 512 B | L² × 1,536 B |
| INT8（v4） | L² × 132 B（含 scale） | L² × 512 B（輸出仍是 FP32） | L² × 776 B |

總佔用量**約減半** → 相同記憶體下，L 約可增加 √2 ≈ **1.4 倍**。
（若輸出也量化，才會接近 2 倍，可以當延伸題目。）
> 注意：這是和**我們自己的 FP32 版本**比。LightNobel 的比較基準是 FP16（2.1 節），以 FP16 為基準時 z 只佔 256 B，
> 量化 a、b 的效果會變小；和論文比較時請用 9.4 節的 FP16 數字。

### 這是「解法」的原因
量化同時縮小兩件事：**搬運量**（公式中的分子）和**記憶體佔用**（決定 L 的上限）。
在 v0～v4 裡，這是唯一一個**直接處理「序列長度受限」**的手法，也是 LightNobel 的核心。
（另一類處理容量的手法是「不存中間值」：融合、重算、LightNobel 的 token-wise attention，見第 3 章與 5.4 節。）

## 本章小結

| 問題 | 答案 |
|---|---|
| 量化在做什麼？ | 用低位元整數 ＋ 一把尺記錄數字；還原 = 尺 × 整數 |
| 為什麼 per-token？ | 尺只需涵蓋自己的 128 個數，刻度細；outlier token 不會拖累別人 |
| 尺的成本？ | 每 128 個數一個浮點數，約 1～3% |
| 尺什麼時候乘？ | 沿同一個 token 加總（linear）可以最後乘一次；跨 token 加總（本專題的 einsum）每項都要乘 |
| 效益？ | 資料量變 1/2～1/4；同時降低搬運量與容量需求 |
